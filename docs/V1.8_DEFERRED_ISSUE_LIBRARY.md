## V18-001 — Student Active/Inactive fails for an apparently logged-in owner

### Evidence

- The owner can still navigate the Room-backed app, but `updateStudentProfile` rejects the secure write with `Sign in is required.`
- Earlier live-function inspection found unauthenticated `updateStudentProfile` failures with no Firebase actor UID.
- This is consistent with the app retaining a local `SessionManager` identity while `FirebaseAuth.currentUser` or its usable ID token is absent.

### Impact

- Some owners cannot activate or deactivate a student.
- The existing student, enrollment, fee, attendance, and history records are not supposed to be deleted by this rejected request.
- Repeated taps create frustration but should not be treated as successful updates.

### Temporary workaround for Version 1.7

1. Fully log out.
2. Log in again using the Admin email and password, not a local-only/biometric restoration path.
3. Retry the status change once.

### Version 1.8 fix requirements

- Require a valid Firebase-authenticated user before entering or continuing protected owner/staff screens.
- Make biometric/remembered login restore Firebase authentication, not only the local session.
- Route `updateStudentProfile` through the shared trusted callable path that performs one forced token refresh and one idempotent retry on `UNAUTHENTICATED`.
- If no Firebase user exists, stop before the write, clear the busy state, and show a clear `Session expired. Please sign in again.` action.
- Preserve existing student data and do not convert `PERMISSION_DENIED` into an automatic logout.

### Acceptance tests

- Valid owner can activate and deactivate a student.
- Expired token is refreshed once and the operation succeeds without duplication.
- Missing Firebase user redirects/prompts for login and never reports success.
- Offline/network failure does not change local status falsely.
- Existing batches, fees, attendance, and history remain unchanged across both status transitions.

### Required real-device release checks (run later, before Version 1.8 release)

- Install the eventual Version 1.8 build on a physical Android phone using a real owner account; activate and then inactivate one safe test student, confirming the list, profile, dashboard count, Room cache, and Firestore status agree after refresh.
- Log out, sign in again by Admin email/password, then repeat both status changes once.
- Enable/use remembered or biometric login where available, force-close/reopen the app, then attempt a status change. It must either succeed after one safe token refresh or show `Session expired. Please sign in again.` without changing the student.
- Turn off the network before confirming a status change. The progress state must stop and the student must retain the previous status locally and after reconnecting.
- Use an account without student-management permission and confirm it receives an authorization error, with no retry loop and no automatic logout.
- Confirm a status change does not alter student fees, receipts, attendance, batch enrolments, archive state, or student login access.
- Repeat on at least one lower-spec/older Android device and one current Android device before production release.

## V18-002 — Payment deletion fails with `Sign in is required.`

### Evidence

- The live UI reaches `Delete Payment?`, changes the button to `Deleting...`, and receives `Sign in is required.`
- `UnifiedCollectScreen` calls `FeeCollectionRepository.ownerDeletePayment`.
- The repository sends the `owner_delete_payment` action through `commitFinancialOperation`.
- The backend intentionally rejects requests without `request.auth.uid` in `functions/src/financialLedger.js`.
- `FirebaseFinancialLedgerGateway` currently makes a direct callable invocation instead of using `callTrustedFunction`, so it does not perform the existing one-time token-refresh/retry behavior.

### Classification

- The backend security check is correct and must remain.
- The primary defect is client authentication/session recovery and callable handling, not the payment calculation or Firestore delete transaction.
- On this rejected path, the canonical payment and receipt should remain intact because local deletion is applied only after a successful backend result.

### Temporary workaround for Version 1.7

1. Do not repeatedly press Delete.
2. Fully log out.
3. Log in using the Admin email and password.
4. Reopen the student ledger and retry once after confirming the payment still exists.

### Version 1.8 fix requirements

- Move `FirebaseFinancialLedgerGateway.commit` to the trusted authenticated callable path.
- Keep the same stable `operationId` during the one-time retry so the financial operation remains idempotent.
- Before invoking a destructive financial operation, verify that `FirebaseAuth.currentUser` exists.
- On a missing user, immediately release `Deleting...`, retain the dialog/payment, and show a session-expired login action.
- Retain the durable outbox state and reconcile from the authoritative cloud result before permitting a second deletion attempt.
- Never make `commitFinancialOperation` public in a way that bypasses Firebase callable authentication, and never remove its `request.auth.uid` authorization check.

### Acceptance tests

- Authenticated owner can delete an eligible payment; its receipt is removed and applicable fee returns to Due.
- A stale token refreshes once using the original operation ID and cannot double-delete or double-adjust the fee.
- Missing Firebase user produces a session-expired UI without deleting Room or cloud records.
- Timeout/response-loss recovery reconciles the server result before retrying.
- Unauthorized staff and cross-institute users remain blocked.
- The progress state always stops on success, rejection, cancellation, and network failure.

## Shared Version 1.8 authentication work package

Both issues should be solved as one narrowly scoped session-hardening package:

1. Audit every authenticated callable gateway and list whether it uses `callTrustedFunction`.
2. Repair biometric/remembered-session restoration so local authorization cannot outlive Firebase authentication.
3. Standardize `UNAUTHENTICATED` handling: one safe refresh/retry, then session-expired UI.
4. Preserve `PERMISSION_DENIED` as an authorization error, not a token-refresh loop.
5. Add instrumentation containing function/action, app version, auth-present boolean, retry count, and operation ID hash—never passwords or raw tokens.
6. Run emulator tests, Android unit tests, upgrade tests, and physical-device password/biometric/session-expiry scenarios.

## V18-003 — Due selection collision and admission-discount inconsistency

### Evidence

- The Collect Payment screen builds virtual monthly, admission, and course dues before a canonical fee document exists. Each virtual item currently uses `id = ""`.
- Selection state compares only `fee.id`. Therefore every virtual due with an empty ID can appear selected at the same time.
- Resolving the selected due uses the first matching ID. Tapping a different virtual due can consequently resolve back to the first virtual item.
- The ledger load also automatically selects the first due, making the collision look like an unchangeable default selection.
- A virtual admission fee sends its entered discount while creating the canonical fee, but an already-persisted admission fee uses ordinary `collectPayment` and does not send the newly entered discount.
- Pressing `Full` in existing-due mode resets the collection amount to the undiscounted due.
- Pre-save receipt text reads the old stored discount and computes remaining due from the undiscounted amount. Its batch/type can also come from general screen state instead of the selected due.
- No focused regression test currently covers virtual-due identity, explicit single selection, admission discount, Full/Partial behavior, and canonical receipt values together.

### Impact

- Admission and multiple monthly dues can all look selected.
- The owner may be unable to switch between virtual dues reliably.
- A payment intended for one virtual month could be submitted against the first matching virtual due. This is a financial data-integrity risk, even though occurrence in production has not yet been proven from ledger records.
- Discount can appear to reduce the UI amount but remain unapplied to an existing admission fee, leaving an unexpected balance due.
- A newly created discounted admission fee can be correct in the backend while its prebuilt receipt incorrectly shows no discount or a remaining due.
- The due list is alphabetically sorted by label rather than chronologically, producing orders such as Admission, Aug, Jul, Jun.

### Temporary guidance for Version 1.7

- If multiple cards are highlighted, do not collect the payment from that screen state.
- Do not rely on the admission-discount field for an admission fee that already exists in the ledger.
- Confirm the selected fee period, batch, payable amount, and generated receipt before treating the collection as complete.
- Do not repeatedly submit after an ambiguous or failed result; refresh the ledger first.

### Version 1.8 fix requirements

- Give every due a stable UI selection key. A real due may use `fee:<feeId>`; a virtual due should use a composite such as `virtual:<feeType>:<batchId>:<period>:<sourceId>`.
- Keep this UI key separate from the canonical Firestore fee ID; never send a fabricated fee ID to the backend.
- Prefer no automatic due selection. Require one explicit selection before enabling Save, and ensure exactly one card is highlighted.
- For a virtual admission fee, create the fee with the entered discount and payment in the existing trusted ledger transaction.
- For an existing eligible admission fee, use the trusted `adjust_and_collect` operation so the canonical base amount, discount, payable amount, payment, and receipt change atomically.
- For a partially paid fee, reject a discount that would reduce the new total below the immutable amount already paid.
- Make `Full` equal the canonical discounted total minus effective payments. `Partial` must remain bounded by that amount.
- Build the displayed/shared receipt from the canonical backend result, not pre-save screen calculations.
- Resolve receipt batch, fee type, period, discount, collected amount, and remaining due from the actual selected/canonical fee.
- Sort monthly dues by parsed year/month, with one-time fee placement defined explicitly.
- Deduplicate due rows by their stable business identity before rendering.

### Acceptance tests

- Admission, Jun, Jul, and Aug virtual dues each have distinct selection keys and exactly one can be selected.
- Selecting each virtual due submits the matching batch, fee type, and period.
- No due is selected on initial load; Save remains disabled until the owner chooses one.
- A new BDT 500 admission fee with 10% discount records base 500, discount 50, total/collection 450, and due 0.
- An existing unpaid admission fee applies the same discount through `adjust_and_collect`.
- A partial prior payment cannot be invalidated by an excessive discount.
- Full respects the discount; Partial cannot exceed the discounted outstanding balance.
- UI summary, Firestore fee, payment, receipt, Room cache, printed PDF, WhatsApp text, and student profile all show the same canonical values.
- Alphabetic month-order regressions and duplicate rendered dues are covered by tests.

## V18-004 — Full fee waiver and consolidated multi-month receipt

### Evidence

- A 100% discount makes the payable/collection value zero. The UI converts a non-positive amount to an empty string and requires `collecting > 0`, so Save is disabled.
- The normal backend `collect_payment`/`adjust_and_collect` path requires a positive payment amount. It cannot represent an adjustment-only full waiver for an existing fee.
- The `create_fee` path can create a zero-total fee without a payment, but the current UI and result handling assume a payment/receipt flow and do not expose a proper waiver confirmation.
- Multi-month Save loops through the selected months and calls `collectPayment` or `createFeeWithInitialPayment` separately for each allocation.
- The calls share a `receiptGroupId`, so the backend can reuse one receipt number, but each payment still creates a separate receipt document tied to one payment.
- The separate calls are not one atomic financial operation. If a later call fails, earlier months may already be committed.

### Impact

- An owner cannot intentionally waive 100% of an admission or other eligible fee.
- Treating a waiver as a zero-taka cash payment would be misleading accounting, so simply enabling the existing Save button is not sufficient.
- A four-month collection can appear as multiple receipt cards/PDFs rather than one customer-facing receipt with four line items.
- Response loss, authentication expiry, network failure, or validation failure between monthly calls can leave a partially completed group.
- Repeated attempts after a partial result can confuse the owner and require reconciliation, even though per-operation idempotency protects an individual allocation.

### Correct accounting model

- Keep one internal fee/payment allocation per covered month for accurate monthly dues and reversals.
- Create one canonical receipt header for the collection and attach every monthly allocation as a receipt line item.
- The guardian-facing PDF, WhatsApp text, print view, and payment-history group should show one receipt number, every covered month, discount details, and one grand total.
- A 100% discount should be recorded as a fee waiver/discount adjustment with zero collected, zero due, actor, reason, timestamp, and audit history—not as a cash payment.

### Version 1.8 fix requirements

- Add a trusted adjustment/waiver operation for a full discount with no payment. It must support both a newly materialized virtual fee and an existing eligible fee.
- Require a waiver reason and preserve immutable prior payments. A waiver must be rejected if its adjusted total would fall below the amount already paid.
- Give the settled fee an explicit canonical representation such as a zero-total `paid` fee plus adjustment metadata, or a dedicated `waived` status consistently supported by every calculator and screen.
- Generate a canonical Fee Waiver/Discount Confirmation containing base amount, 100% discount, payable zero, collected zero, due zero, actor, and reason.
- Add one trusted grouped-collection backend action that receives all intended monthly allocations, validates them first, and commits the fee updates, payments, receipt header, receipt items, and audit record in one Firestore transaction.
- Use one stable group operation ID and one receipt number. A retry must return the original result and must not duplicate payments, receipts, or monthly allocations.
- Store one receipt header with student, date, method, total collected, total discount, and status; store or embed line items containing fee ID, batch, period, fee type, base, discount, collected, and remaining due.
- Apply Room changes in one local transaction only after the authoritative backend result. A response-loss retry must reconcile the canonical group before resubmission.
- Render one grouped entry/PDF/message while retaining month-level ledger details for internal accounting, edits, reversals, and reporting.
- Define safe behavior for deleting or reversing one line versus the whole grouped receipt; totals and receipt status must remain consistent.
- Remove the backend receipt-group ten-minute timing dependency from correctness. Expiry may limit abandoned groups, but it must not cause a partially committed Save action.

### Acceptance tests

- A BDT 500 fee with 100% discount saves base 500, discount 500, payable 0, collected 0, and due 0 without creating a false cash payment.
- The waiver confirmation and audit record identify the fee, actor, reason, and timestamp.
- A partial prior payment prevents an invalid waiver below the immutable paid total.
- Four monthly fees collected in one action create four internal allocations and exactly one grouped customer receipt with the correct grand total.
- Failure in any line validation commits no month, payment, receipt, or adjustment.
- Network/response loss followed by retry returns the same group and does not duplicate any line.
- Payment history, PDF, print, WhatsApp, Room, Firestore, due summary, and student profile display matching grouped totals and month details.
- Reversal/deletion tests keep the receipt header, line items, monthly fees, and overall status consistent.

### Local implementation record — 11 Sep 2026

- Added trusted `waive_fee` backend action: settles a full one-time waiver with zero collected and zero due, requires a reason of at least 3 characters, rejects a waiver that would fall below immutable prior payments, records an immutable `fee_waived` audit event, and never fabricates a zero-value cash payment. It supports both a canonical fee ID and a newly materialized virtual fee.
- Added trusted `collect_grouped_payment` backend action: validates every monthly allocation first, then commits the fee updates, payments, one receipt header with per-month line items, and the audit record in one Firestore transaction. It uses one stable group operation ID and one receipt number; a replay returns the original result without duplicating payments, receipts, or allocations.
- The Android repository exposes `waiveFee` and `collectGroupedMonthlyPayment` through the same trusted gateway; Room is updated only from the canonical backend result. The collection screen enables Save for a 100% waiver only with a reason, shows a waiver confirmation instead of a cash receipt, and renders one grouped entry while retaining month-level ledger detail.
- Verification completed locally: Kotlin unit/debug compilation, backend ledger tests including full waiver, atomic grouped collection, invalid-allocation rejection and idempotent replay, and the Firestore rules suite. No Firebase deployment, release build, or production data change was made.

## V18-005 — Custom Monthly Fee Effective Period UX

### Confirmed current behavior

- The Custom Fee dialog calculates the effective period from the device's current month and only displays it as informational text.
- The owner cannot select whether the custom fee starts in the current month, next month, or another future month.
- The backend independently calculates the effective period using Asia/Dhaka server time.
- After backend success, the app can retain its locally calculated period instead of the canonical period confirmed by the backend. A wrong device date or a month-boundary request can therefore create a local/cloud display mismatch.
- Previous arrears and completed or partially paid fee records are not intended to be rewritten by the current backend behavior.

### Impact

- This is not a direct data-loss defect, but an owner can reasonably assume that the custom amount applies to a different month than the system uses.
- Silent skipping of a selected month that already has a payment can create financial confusion.
- The effective custom-fee policy is not prominent enough on the student profile for an owner to verify it later.

### Version 1.8 UX requirements

The Custom Fee dialog must clearly show:

- `Batch fee: BDT 1,000`
- `Custom monthly fee: BDT 700`
- `Effective from:`
  - `Current month — Sep 2026`
  - `Next month — Oct 2026`
  - `Choose future month`
- Reason
- A confirmation summary before saving

Example confirmation:

> From Sep 2026, this student’s monthly fee will be BDT 700 instead of BDT 1,000. Previous months and completed payments will remain unchanged.

The student profile must show a persistent badge such as:

> Custom fee: BDT 700 · From Sep 2026

### Business and data rules

- A past month must not be selectable as the effective period.
- If the selected month's fee is already paid or partially paid, the change must not be silently skipped.
- In that case, show a clear message such as: `September has an existing payment. Select October 2026 or a later month.`
- Restoring `Use batch fee` must also require an effective month; it must not retroactively rewrite older dues.
- The backend must validate and return the canonical effective period. The app and Room cache must store that returned value rather than recomputing it from device time.
- Previous payments, receipts, settled fees, and audit history must never be rewritten by a custom-fee policy change.
- A correction to a previous month must use a separate, explicitly audited Fee Correction/Adjustment flow rather than the Custom Monthly Fee dialog.

### Acceptance tests

- Current, next, and a valid future month can be selected and the confirmation text matches the selection.
- Past periods are disabled and cannot be submitted by a crafted client request.
- A paid or partially paid selected period is rejected with the clear next-month guidance.
- An unpaid eligible current/future fee and future virtual dues use the new custom amount from exactly the canonical effective period.
- `Use batch fee` follows the same effective-period rules.
- Device timezone/date disagreement at a month boundary cannot produce a Room/Firestore effective-period mismatch.
- Student profile, due calculation, payment collection, Room, Firestore, and audit history show the same custom amount and effective period.
- Existing payments and receipts remain byte-for-byte financially unchanged after setting or removing a custom fee policy.

### Local implementation record — 11 Sep 2026

- The Custom Fee dialog now offers `Current month`, `Next month`, and `Choose future month` with a confirmation summary; a past period cannot be selected and a paid/partially paid selected period is rejected with next-month guidance.
- `set_custom_monthly_fee` now accepts an explicit `effectiveFromPeriod`; the backend validates it (not in the past, within 60 months), rejects a selected month that already has payments, returns the canonical effective period and a machine-readable `customFeePolicyTimeline`, and the app stores only those confirmed values in Room instead of recomputing from device time.
- Restoring `Use batch fee` follows the same effective-period rules, and the due list renders first-month proration so a custom policy is visible at collection time.
- Room migration 43-to-44 adds `customFeePolicyTimeline` without clearing existing rows.
- Verification completed locally: Kotlin unit/debug compilation, backend ledger tests for current/next/future periods, past-period rejection, existing-payment rejection and timeline encoding, and the Firestore rules suite. No Firebase deployment, release build, or production data change was made.

## V18-006 — Student Late Attendance and Arrival Time

### Confirmed current behavior

- The owner-facing student attendance workflow currently offers `Present`, `Absent`, `Leave`, and `Holiday`.
- `Holiday` is modeled as an individual student's status even though a holiday or cancelled class normally applies to the entire batch/date.
- The student app already recognizes and displays the string status `late`, but the owner attendance workflow, summaries, dashboard, student profile, and PDF/report paths still calculate and render `holiday`.
- `AttendanceEntity` contains status and note fields but has no structured arrival time, scheduled-start snapshot, or late-duration fields.
- A batch already stores schedule days, start time, and end time.

### Product decision

- Replace the new-marking `Holiday` action with a complete `Late` action for student attendance.
- Keep all historical `holiday` records readable. They must not be deleted, rewritten, or automatically converted.
- Treat a future batch-wide `Holiday / No Class` capability as a separate calendar/session feature rather than a per-student attendance status.

### Recommended marking UX

The available student actions should be:

- `P` — Present
- `A` — Absent
- `Lv` — Leave
- `Lt` — Late

Selecting `Late` must open a confirmation/time picker showing:

- Scheduled class start time from the batch
- Arrival time, initially set to the current time for today's attendance
- Calculated `Late by N minutes`
- Cancel and Confirm actions

For a past attendance date, the owner must explicitly select the arrival time rather than inheriting the current clock time.

### Required canonical data

A confirmed late record should preserve structured values equivalent to:

- `status = "late"`
- `arrivalTimeMs`
- `scheduledStartTime` or an equivalent schedule snapshot
- `lateByMinutes`
- Existing attendance date, batch, student, actor, created-at, and updated-at values

The scheduled-start snapshot is required so editing a batch schedule later cannot recalculate or corrupt historical late durations. Arrival timing must not be encoded only inside the free-text note.

### Validation and calculation rules

- `Late` is valid only when arrival time is later than the scheduled start time.
- If arrival is at or before scheduled time, prompt the owner to mark the student Present instead.
- If the batch has no usable start time, require the owner to provide a scheduled time or direct them to complete the batch schedule; do not silently calculate an incorrect duration.
- Count `Present + Late` as attended.
- Calculate attendance rate from `(Present + Late) / (Present + Late + Absent)` under the final approved Leave policy.
- Calculate punctuality separately as `Present / (Present + Late)`.
- Display Late count and, where useful, average late minutes separately from attendance rate.
- Absence messages must continue to be generated only for `Absent`; adding Late must not accidentally send absence notifications.
- `Mark All Present` can remain. A `Mark All Late` action is not required.

### Version 1.8 implementation scope

- Add a safe Room schema migration for the structured late fields.
- Add matching Firestore serialization, download/rebuild, and backward-compatible parsing.
- Preserve the atomic bulk-attendance write behavior and support mixed statuses/timing values safely.
- Update owner attendance UI and its confirmation/time picker.
- Update batch/day/month summaries, dashboard, student profile insights, student-app calendar, exports, PDF, and message/report formatting.
- Continue recognizing legacy `holiday` records in historical summaries without offering Holiday as a new per-student action.
- Define a distinct color and label for Late; use `Lv` and `Lt` so Leave and Late cannot both appear as ambiguous `L`.

### Acceptance tests

- Present, Absent, Leave, and Late can each be selected independently and remain correct after cloud sync, reinstall, and full Room rebuild.
- Marking Late at 6:17 PM for a 6:00 PM class stores and displays 17 minutes late.
- An arrival at or before class start cannot be saved as Late.
- A past-date Late action never uses today's current clock accidentally.
- Changing the batch time later does not change an existing late record or its displayed duration.
- Attendance rate includes Late as attended, while punctuality distinguishes Present from Late.
- Dashboard, student profile, student app, Room, Firestore, PDF, and exports agree on status and timing.
- Existing historical Holiday records remain visible and unchanged after migration and reinstall.
- Absence notifications are not sent for Present, Leave, Late, or a legacy Holiday record.
- Offline/error and retry paths cannot create duplicate attendance rows or lose an earlier confirmed status.

### Local implementation record — 11 Sep 2026

- The owner marking workflow now offers `P`, `A`, `Lv`, and `Lt`; `Holiday` is no longer offered as a new per-student action, while existing `holiday` rows stay readable as legacy history.
- Selecting `Lt` opens a confirmation/time picker showing the batch's scheduled class start, the arrival time, and a live `Late by N minutes` calculation. Arrival at or before the scheduled start is rejected with `Mark the student Present instead` guidance; a batch without a usable start time requires the owner to supply the scheduled time. A past attendance date never inherits the current clock.
- `AttendanceEntity` gains structured `arrivalTimeMs`, `scheduledStartTimeMs`, and `lateByMinutes` fields (Room migration 44-to-45, non-destructive), serialized in the atomic bulk attendance path and the student app calendar. Changing a batch schedule later cannot recalculate historical late durations because the scheduled start is frozen at marking time.
- Attendance rate counts `Present + Late` as attended; punctuality is reported separately as `Present / (Present + Late)`. Dashboard, batch/day/month summaries, student profile, report text, and the student app show Late count and average late minutes; absence notifications remain Absent-only.
- Verification completed locally: Kotlin unit/debug compilation, Android unit tests including late-attendance summary/migration coverage, backend and Firestore rules suites. Physical-device acceptance testing and Firebase deployment remain pending.

## V18-007 — Platform Team Member Accounts and Role-Based Console

### Local Version 1.8 implementation record — 9 Sep 2026

- Added a Root-only `Team Members` management area: invite a non-root platform member, list safe member metadata, change a member role, suspend, and reactivate. Root creation remains unavailable.
- Added trusted `list_platform_admins` and `update_platform_admin` callable actions. Role/status changes use an idempotency operation ID and append immutable platform-audit entries with actor, target, before/after state, timestamp, and reason.
- Added distinct role consoles: Support (owner recovery), Billing (subscription requests), Operations (institute onboarding/import/owner transfer), and Read-only (dashboard only). The server remains the final permission authority.
- Suspended or unconfirmed platform accounts cannot fall back to a stale local platform session. They are signed out instead.
- Tightened Firestore `app_users` access: non-root members may read only their own active record; the team directory is returned only through the Root-only callable and excludes secrets, recovery links, and tenant identity.
- Verification completed locally: Kotlin debug compile, platform backend tests, and Firestore emulator rules tests. No Firebase deployment, Firebase data change, APK release, or live-user change occurred.

### Business need

The BatchFee owner needs to delegate platform work to an internal team without sharing the Root/Super Admin account. A team member must receive an individual platform account, then see and perform only the support, billing, operations, or reporting tasks assigned to that account.

### Important identity rule

- A BatchFee platform team account is not an institute Staff account.
- Institute staff IDs such as `STF...` remain restricted to a single client institute and must never grant BatchFee-wide administration access.
- A platform team member must sign in through `Admin` using their own email and password. Passwords and recovery links must never be visible to another team member after provisioning.

### Confirmed current behavior

- The platform backend already recognizes `root`, `billing`, `support`, `operations`, and `read_only` platform roles.
- A Root user can provision a non-root platform account through the trusted `manage_platform_admin` operation. The system creates or reuses a Firebase Auth identity and returns a password-recovery link so the new team member can set their own password.
- A platform account cannot be converted from or merged with an institute account. This protects institute staff/owners from accidental cross-tenant privilege escalation.
- Root provisioning of another Root account is intentionally blocked from the client UI.

The final action matrix must be implemented server-side; hiding a UI button alone is not security.

## V18-010 — Secure credential recovery instead of password reveal

### Confirmed current behavior

- Firebase Auth owner/admin passwords are intentionally non-recoverable. Firebase can authenticate a supplied password or set a new one, but cannot return the existing secret.

- Require the recipient to change a temporary password on first successful login where the credential type supports it; preserve a safe fallback for low-connectivity/support cases.
- Record an immutable audit record containing actor, target account, target type, institute, reason, timestamp, and result — never the password itself.

### Confirmed current behavior

### Notice Center UX

Each notice card must show:

- Category: `Update`, `Maintenance`, `Billing`, `Feature`, or `Important`.

- `App-version audience`: allow an optional minimum/maximum app version so an upgrade or maintenance message reaches the relevant release population.

- Store each recipient's read state separately, keyed by user/institute plus notice ID. A user may create/update only their own read marker; they must not alter notice content, other users' read state, or audience fields.
- The trusted server creates/edits/publishes/archives a notice and enforces platform role, audience limits, message length, idempotency, and audit logging. Do not let a Super Admin client write unrestricted global documents directly.
- Publishing, editing, archiving, audience changes, and critical-push decisions must be immutable-audited. Read receipts should record only user/account ID, notice ID, and timestamp; no device identifiers, passwords, tokens, or message content belong in read markers.
- Use paging and bounded queries for notices/read state. Do not fan out a duplicate full message document to every user for large audiences unless a server-side scale review proves it safe.

- A long Bengali/English notice is readable in full from the Notice Center and is never clipped permanently.
- A normal notice produces an unread bell dot/count without a popup, sound, or forced navigation.
- Read state persists after app restart, reinstall/rebuild, and opening the account on another device.
- An eligible old user who returns before expiry sees the notice; an expired/archived notice does not appear as unread.
- A `today`/recently-active audience uses server-confirmed Asia/Dhaka activity data and excludes non-target roles/institutes.

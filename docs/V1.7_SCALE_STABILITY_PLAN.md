# BatchFee 1.7 — Scale & Stability First

Version 1.7 starts with reliability and scale work before any new feature or broad UI change.

## Priority order

1. Replace full-collection refreshes with incremental sync based on changed records.
2. Add pagination/chunking for students, fees, payments, receipts, attendance, activity, and audit history.
3. Apply Firestore realtime document changes directly to Room instead of re-downloading whole collections.
4. Move dashboard totals and counts to trusted server-maintained summary documents where appropriate.
5. Tune Cloud Functions capacity, concurrency, timeouts, retries, and idempotency per operation.
6. Finish authentication refresh and permission-denied handling for long-running sessions.
7. Paginate Super Admin receipts, audit history, and other unbounded collection listeners.
8. Add monitoring and billing/latency/error alerts.
9. Run staged load tests for 100, 500, and 1,000 concurrent requests and large institute datasets.

## Existing core issues included in the stability phase

- Staff account creation and staff login reliability.
- Student registration link, approval, and crash protection.
- Archive permanent-delete authentication refresh and retry handling.
- Remaining Crashlytics `PERMISSION_DENIED`, authentication, network, and cancellation noise.

## Release gates

- Crash-free users: at least 99.5% over a meaningful 7-day sample.
- Crash-free sessions: at least 99.8% over a meaningful 7-day sample.
- No duplicate records from repeated Save, Approve, or Submit taps.
- Room cache renders primary screens without waiting for the network.
- Large institute histories do not require a full cloud collection download on each change.
- The 1,000-concurrent-request test completes without data corruption or unacceptable error rates.

Do not begin non-essential Version 1.7 features until these stability gates are addressed and verified.

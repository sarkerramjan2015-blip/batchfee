# BatchFee 1.7 implementation checkpoint — 7 September 2026

This supersedes the implementation status (not the findings) in the 6 September audit. Changes are local and uncommitted. No production Firebase deployment, customer-data mutation, APK installation, AAB publishing, or signing change was performed.

## Implemented locally

- Billing/date consistency: legacy monthly start dates prefer admission over sync/join timestamps. New enrollments explicitly record whether they follow admission; admission edits do not silently move independent assignments or course charges. Room 41-to-42 adds a nullable field without clearing rows.
- Assignment flow: first assignment defaults to admission, later assignment to the selected assignment date. A new authenticated server transaction creates enrollment and course charge together. Operation replay reads current fee/payment state; same-actor retries can recover the prior enrollment. A student-document write serializes competing new-endpoint transactions. Local enrollment and returned fee are stored in one Room transaction only after server success.
- Batch creation retries reuse a stable operation ID derived from the batch ID. This is not a durable offline outbox.
- Staff login mapping now retains category, salary type/rates, and subject information instead of replacing these fields with defaults.
- Temporary student-session network failures do not destroy the Firebase login; UI access remains closed until validation, with a resume retry. Duplicate login taps are ignored while loading and a successful login clears the password field.
- Permanent archived-student purge now also removes student-scoped payment reversals on server and locally. Deletion metadata writes are chunked to 400. Restore/delete UI releases its busy state before waiting for the snackbar, and cancellation is rethrown. Local records are still removed only after server success.

## Not production-ready yet

1. **Deployment dependency:** the new Android enrollment path requires `enrollStudentInBatch`. It must not be released before a separately reviewed compatible backend deployment. No such deployment has occurred here.
2. Existing 1.6 direct enrollment writes remain possible under current rules. The transaction tests establish guarantees for the new endpoint, not every old-client path.
3. Remaining operational write helpers can suppress permission failures. Review each caller's error handling before changing the shared behavior; otherwise a fix could introduce uncaught exceptions.
4. `Demo_Visitors` still has an open read/write rule. Restrict and test it before security sign-off.
5. Cache-refresh completion/freshness reporting and save-latency paths need further work. No measured performance claim is made.
6. Permanent purge is multi-step, not an atomic durable deletion job. Network interruption, restoration races, client/server timeout alignment and retry recovery still need deeper integration coverage. Existing financial-operation/audit retention was not redesigned.
7. Staff/student login on a second real device, upgrade from a populated 1.6 database, offline/reconnect, course editing/creation and complete release smoke testing remain required. The small migration test does not substitute for a full production-data upgrade test.
8. Real deployed backend parity, customer-specific failures, release build/lint, AAB and Play Store readiness remain unverified.

Next phase: permission-failure propagation and caller UI handling, then telemetry rules and cache freshness; rerun regression gates before release preparation.

## Requested performance implementation — subsequent checkpoint

Implemented locally (not deployed):

- Bulk attendance, ordinary exam result save, and result publish now use a single Firestore WriteBatch per operation and a Room transaction after acknowledgement. Permission/network failures propagate rather than producing local success. Attendance resolves legacy document IDs before committing; newly created marks use deterministic IDs. Single attendance marking uses the same path. Bulk errors are displayed.
- A whole operation is limited to 400 writes (399 results plus exam completion). Larger requests fail before any write, rather than silently committing partial chunks. This is an explicit current limit, not unlimited bulk support. Existing duplicate attendance history is rejected for reconciliation rather than silently deleting cloud history.
- Shared staff activity logging and staff login logging enqueue durable Room records; delivery no longer blocks the success callback. Institute dashboard profile edits are saved locally with a durable profile task; UI says cloud sync is queued. Media upload still completes before queuing its reference. Authentication/credential/billing-related student and staff profile writes remain server-confirmed.
- The background runner retries while the process is alive and resumes persisted tasks when the app starts again. It is not a WorkManager job and does not guarantee delivery while the app is force-stopped. Pending jobs are isolated by Firebase actor and institute; profile writes stay ordered and do not include subscription/counter fields. Pending local profile fields are preserved during institute refresh.
- Room migration 42-to-43 adds the queue without deleting existing data. Existing 41-to-42 remains registered.
- A narrow audit-log rule permits only identical retries by the original active staff author. Log edits and other authors' replays remain denied. **This local rule change must be reviewed/deployed before release for reliable acknowledgement-loss replay; it has not been deployed.** Without it, affected retries remain queued rather than being discarded.

Verification at this checkpoint: Android BUILD SUCCESSFUL, 66 tests with zero failures/errors; local demo Firestore rules suite 45 passed, including 400 attendance writes, 399 results plus exam completion, rejection without a partial write, and immutable audit replay. Source whitespace check passed. No real-device speed measurements or release/AAB validation were performed. Cloud commit and Room commit cannot be one distributed transaction: a process crash between them still requires the existing cloud-to-Room refresh/retry; no universal mismatch-free guarantee is claimed. Existing real-time listeners may render changes incrementally; these tests verify server write atomicity and the mutation path's local transaction, not atomic rendering on every connected screen.

# BatchFee 1.7 production-readiness audit — 6 September 2026

## Verdict and scope

**Do not sign off this revision for production yet.** There are confirmed billing inconsistencies, false-success write paths, and incomplete enrollment/deletion safeguards.

Audited local Git HEAD `17f6ce6`, versionName `1.7`, versionCode `11`, Room schema `41`. Reviewed staff/student authentication, course creation, enrollment/assignment dates, billing, deletion, and sync/latency paths. This is a targeted source-and-local-test audit, not an assertion that every screen or device was exercised.

No application source, backend source, rules, production data, or deployment was changed. No APK was installed, no AAB was produced, and no commit was made. This report and generated test/build/log artifacts are the audit outputs. Existing unrelated untracked files were left alone.

The deployed Functions/rules revision, customers' installed builds, production logs, and real-device login were **not verified**. ADB listed no connected device. Local code support does not prove that the same implementation is deployed or installed.

## Findings requiring fixes or an explicit product decision

### F01 — High: Android and backend disagree on legacy billing start

Evidence: `app/src/main/java/com/example/domain/MonthlyDueCalculator.kt:139`; `functions/src/financialLedger.js:102`.

Without `firstMonthFeePeriod`, Android prefers `joinedAtMs`; the backend prefers the student's admission month. An older enrollment can contain a later sync/join timestamp, so Android can hide legitimate arrears while the server still considers those months billable. Student-side billing also uses this Android calculator (`StudentBillingSummaryCalculator.kt:97`).

Fresh tests demonstrate the discrepancy:

- A June fee expected to be inside the legacy enrollment window is rejected by Android.
- A legacy student admitted in June with an August join timestamp should have June/July outstanding according to the existing test contract; Android returns an empty list.

Fix direction: distinguish migrated/legacy first enrollment from explicitly dated later assignment, freeze its contractual billing start, and apply the same policy on server and client. Do not simply change the tests or universally backdate all later batches to admission.

### F02 — High: assignment date depends on which screen is used

Evidence: `StudentProfileScreen.kt:1206`, `BatchDetailScreen.kt:1579` under `app/src/main/java/com/example/ui/`.

- Student Profile opens an assignment-date dialog, but defaults to **now**, even for the first batch.
- Batch → Enroll Students always supplies **student admission date**, including second/subsequent batches; this route has no date selection.

Thus the requested first-batch/admission-date and later-batch/explicit-date policy is not consistently implemented. A later assignment may acquire earlier fees merely because it was made from the Batch screen.

Fix direction: share one assignment dialog/policy across entry points. Default the first enrollment to admission date; require an explicit date for later assignments, and preserve that date independently of future admission edits.

### F03 — High: course enrollment and its ledger fee are separate operations

Evidence: `app/src/main/java/com/batchfee/edu/data/repository/BatchEnrollmentRepository.kt:69` and `:258`; `functions/src/financialLedger.js:222`.

The flow writes enrollment to Firestore, then Room, and only afterward requests the course fee. A crash between these steps can leave an enrollment without a ledger fee. A rejected fee request also leaves the enrollment in place. The fee repository has a durable outbox once entered, which helps transient failures, but it does not make the preceding enrollment atomic with the fee.

Concrete permission mismatch: staff with `manage_batch` can write an enrollment under the current rules, whereas creating its course fee requires financial authority (`collect_fee` for staff). Such a staff account can reach a partially completed course assignment.

Fix direction: a single trusted, idempotent enrollment transaction should validate membership/permissions and create the required course charge with the enrollment. Decide explicitly whether batch-management permission includes creating the fixed enrollment charge; do not grant arbitrary payment permissions to bypass the problem.

### F04 — High: denied cloud writes can appear successful locally

Evidence: `app/src/main/java/com/example/data/firestore/OperationalDataSyncHelpers.kt:50` and `:59`; `BatchEnrollmentRepository.kt:69`.

`rethrowUnlessAccessDenied()` silently returns for `PERMISSION_DENIED`. `upsertEnrollment()` uses it. Its caller then inserts into Room as though the cloud write succeeded. For monthly enrollment, the operation can return normally despite the denied write. Multiple other operational write helpers use the same pattern.

This is a concrete path to device-only data and misleading success, not merely a slow internet symptom. Expected access loss must stop the operation or return a typed failure; it must not be treated as a committed save.

Fix direction: handle errors at the UI/ViewModel boundary without crashing, preserve genuine pending operations explicitly, and show successful completion only after the appropriate commit acknowledgment. Separate read-listener access loss from failed writes.

### F05 — High: concurrent assignment can create duplicate active enrollments

Evidence: `BatchEnrollmentRepository.kt:48`; `app/src/main/java/com/example/data/models/BatchStudentEntity.kt:9`; `firestore.rules:518`.

Each enrollment uses a random ID. UI in-progress guards protect one screen instance only; the server write does not transactionally claim the active institute/student/batch relationship. Room has lookup indexes, but no unique active-membership constraint. Two devices can therefore create separate active records for the same student/batch.

Potential effects include duplicate list rows, inflated enrollment-derived totals, and ambiguous unassignment/history. Course ledger business-key protection does not prevent duplicate enrollment records.

Fix direction: a server-side active-membership claim plus replayable operation ID. Preserve distinct historical enrollment periods; do not introduce a uniqueness rule that prevents legitimate re-enrollment after removal.

### F06 — High: admission-date correction mishandles courses and same-month assignments

Evidence: `functions/src/financialLedger.js:617` and `:637`; `app/src/main/java/com/example/ui/students/StudentViewModel.kt:392`.

The server treats any enrollment with no frozen month, or with a frozen month equal to the original admission month, as admission-linked. It then validates a positive **monthly** fee for all selected batches.

Two additional probes used the existing in-memory handler test harness, with synthetic data only:

1. Active course, monthly fee 0, course fee 5,000, no frozen monthly period: correcting admission date fails with `invalid-argument: batch monthly fee must be greater than zero.`
2. Admission on 1 September; an independently dated assignment on 20 September, frozen September fee 367: changing admission to 10 August rewrites that independent enrollment to August and 700.

The second case shows that comparing month labels cannot reliably identify the first/admission-linked batch. Both server selection and local reconciliation need an explicit link/type policy. Paid history should remain immutable.

### F07 — Medium: staff login discards teacher compensation fields locally

Evidence: `app/src/main/java/com/example/ui/auth/AuthScreen.kt:384` and `:599`; `app/src/main/java/com/example/data/models/StaffEntity.kt:37`.

The staff profile fetch reads category, salary type, class/hour rates, and subjects, but login constructs `StaffEntity` without these fields. Defaults become administration/monthly/zero rates/null subjects. This can overwrite the correct local row until another sync restores it.

Full staff sync is permission-scoped (`CoreDataSyncPolicy.kt:59`; `RealtimeListenerPolicy.kt:75`), so restoration is not guaranteed for a staff account without staff-management permission. This does not by itself establish that the staff password login fails, or that server salary data is overwritten.

Fix direction: reuse a complete canonical staff mapper for login and all sync entry points; test per-class/per-hour teachers on a fresh device.

### F08 — Medium: a transient student-session validation failure signs the student out

Evidence: `app/src/main/java/com/batchfee/edu/domain/StudentSessionManager.kt:197`.

The validation catch block does not distinguish expired/revoked identity from temporary network/read failure. Once a student token is identified, any exception signs out the same current user and clears the session.

Fix direction: keep protected access blocked when identity cannot be verified, but distinguish temporary verification failure from an actual revoked/expired account. Show retry/offline state instead of unnecessarily destroying an otherwise valid session. Preserve explicit logout on confirmed revocation.

### F09 — Medium: batch creation retry loses its operation identity

Evidence: `app/src/main/java/com/batchfee/edu/data/repository/EntitledCreationRepository.kt:45`; `functions/src/index.js:1116`.

Every `createBatch()` call generates a new operation ID, although the form retains the batch ID while open. If the server commits but the response is lost, pressing Save again sends a new operation and the server can return “Batch already exists” rather than replaying success. Reopening the form generates another batch ID and creates duplicate-intent risk.

Fix direction: persist one operation/entity identity for the pending form and reconcile the canonical saved batch after an uncertain result. A same-call stale-auth retry is already present; this finding concerns a later user retry/process restart.

### F10 — Medium: permanent student deletion leaves related reversal records

Evidence: `functions/src/permanentStudentPurge.js:7`; `app/src/main/java/com/example/data/repository/PermanentStudentPurgeRepository.kt:23`; `PaymentReversalEntity.kt:9`.

Both server and local deletion lists omit `payment_reversals`, even though reversal rows have `studentId`. These records can survive after their student/payment/fee parents are deleted. The UI currently claims all linked data was deleted.

The purge is also a sequence of paged collection deletes followed by media, Auth, login metadata, and profile removal—not an instantaneous operation. A late-stage failure can occur after earlier cleanup has already completed. An authorized retry for an already-missing profile is supported, which is useful, but there is no durable client purge-job state comparable to the archive outbox.

Fix direction: define intentional financial/audit retention versus deletion, clean or retain linked records consistently, and make long purges resumable with visible progress. Do not simply delete locally first or shorten timeouts. The exact cause on a customer's phone still requires its error, role, version, and timestamp.

### F11 — High security boundary: demo telemetry is publicly readable and writable

Evidence: `firestore.rules:912`; `app/src/main/java/com/example/domain/DemoAuthRepository.kt:27`.

`Demo_Visitors/{document=**}` allows read/write unconditionally. Anyone reaching this deployed rule could read or modify the collection without authentication. The application writes guest UID, device model, account type, and activity timestamps there. This finding does not imply all institute data is public, and actual deployed rule parity was not checked.

Fix direction: restrict telemetry reads to appropriate administrators and writes to a validated authenticated identity or trusted endpoint. Preserve the legitimate demo flow. Existing rule tests do not establish this boundary is safe.

## Course creation: what is and is not established

The current local route contains the necessary course fields end to end: `AddEditBatchScreen.kt:478` → `BatchViewModel.kt:49` → `EntitledCreationRepository.kt:115` → `index.js:1095`; `BatchSyncHelper.kt:129` also maps the stored course fields back into Room.

Course fee, dates, and optional schedule validation can legitimately block Save. The examined current code does not establish a universal “course always becomes monthly” defect. If a cloud document lacks billing fields, the current mapper defaults it to monthly/zero course fee, but the audit does not establish why a live document would lack them.

Required next diagnostic: reproduce one create on the actual failing build, capture the displayed error and function response, confirm deployed `createEntitledBatch` revision, inspect that one saved batch document and Room mapping, and reopen on a second device. Do not repair by loosening rules or converting existing monthly batches.

## Login answers

- **Staff ID/password:** current code authenticates through `loginStaff`, receives a custom Firebase token, and fetches managed user/staff records. It is not designed to depend on a pre-existing local Staff ID cache. Cross-device login is supported in design, conditional on a correctly provisioned active account, active institute entitlement, correct password, connectivity, and deployed endpoint. A new-device runtime test remains required; legacy/incomplete account provisioning can still fail.
- **Student ID/password:** custom-token UID/tenant/student checks and remembered Student ID are present. The identified session failure handling still needs correction/testing. Current short-ID reservation and login are **global**, not institute-local (`studentIdCore.js:27`, `index.js:1768`). This differs from the earlier institute-local requirement; settle this explicitly. Shared IDs across institutes require an institute identifier or another unambiguous login design. Do not silently change the namespace and break existing accounts.

## Save/update latency and smoother UX

Confirmed structural contributors, not measured production timings:

- Batch create/update and enrollment wait for cloud acknowledgment before updating Room/completing the form.
- For staff actions, `StaffActivityLogger.kt:43` awaits remote audit logging before the caller returns success. Login also awaits its audit write (`AuthScreen.kt:653`). The business operation may already be complete while the user still waits.
- `CoreDataSyncCoordinator.kt:40` performs multiple collection refreshes sequentially. Full refresh scans can become more expensive with larger institutes.
- `InstituteCacheRefreshManager.kt:62` marks refresh scopes fresh after a coordinator call that may internally swallow failures. Failed refresh should not appear equivalent to synchronized data.
- Permanent deletion legitimately performs more work than removing a visible row.

Recommended design: immediate button feedback and double-submit guards; explicit Saving / Saved / Pending sync / Retry states; durable idempotent queues for eligible non-financial edits; trusted server acknowledgment for fees, identity, and destructive actions; move best-effort audit upload off the critical path using a durable queue; narrow incremental/paged sync and bounded parallel independent reads. Measure tap-to-feedback, server commit, and UI refresh separately on slow connectivity and large synthetic datasets before making speed claims.

## Interpreting the three failing Android tests

The two `MonthlyDueCalculatorTest` failures correspond to F01 and to a real client/server policy disagreement. They must not simply be relabeled green without resolving backward compatibility.

`RealtimeListenerPolicyTest.ownerReceivesCompleteRealtimePlan` expects `listenSalary=false` while the current owner policy returns `true`. This appears to be an outdated expectation after salary realtime support, not proof that enabling owner salary updates is wrong. Confirm the intended permission contract, then update coverage accordingly.

## Suggested repair order and release gate

1. Fix F01/F02/F06 together: one explicit enrollment-date and backward-compatible billing contract.
2. Fix F03/F04/F05/F09: trusted atomic enrollment, explicit write failures, duplicate protection, and stable retries. Reproduce the course-create complaint separately.
3. Fix staff mapping and student session handling; verify ID namespace and new-device login with dedicated test accounts.
4. Address deletion completeness/resumption and the public demo telemetry rule; test restrictive roles as well as owners.
5. Improve save/sync UX with measurements, without optimistic financial/destructive success.
6. Rerun all checks, add regression tests for the reproduced cases, then test a release-like 1.6.3 → 1.7 upgrade with retained Room data, fresh installation/cloud rebuild, offline/reconnect, killed/restarted saves, concurrent two-device operations, Bangla/English input, and low-end devices. Debug compilation is not release validation; the debug database has a destructive fallback that release does not.

Any later backend deployment must remain compatible with live 1.6.3. Do not force all older clients onto new assumptions or broadly open rules. Confirm deployed parity, rollback procedure, signing/versioning, and internal-track runtime results before production publishing. Passing the current unit/rules tests alone is not a thousands-of-users stability guarantee.

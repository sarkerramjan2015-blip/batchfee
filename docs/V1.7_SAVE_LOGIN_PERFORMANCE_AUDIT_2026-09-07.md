# Save / Create / Update / Login performance audit — 7 September 2026

## Result and limits

There are concrete opportunities to shorten completion time, especially bulk attendance, ordinary exam results, final-exam fee generation, and staff audit logging. Not every action is slow for the same reason. Some screens already return after local Room writes; others deliberately require cloud confirmation.

**This is a static, module-level critical-path audit of the current local 1.7 tree, not a measured latency benchmark or proof that every button/branch has been exercised.** ADB returned no connected devices. No matching action timing samples were found in the searched local log/text files. Current action latency, p50/p95, network RTT, backend cold-start contribution, and achievable seconds saved are therefore **not measured for any row below**. No production accounts were exercised and no mutation was sent to Firebase. Only this report was added; app/backend code was not changed for this audit.

The search covered UI mutation methods, repositories, shared sync helpers, login, media, and inline screen saves. Reports/PDF/export are outside save-to-cloud latency; obscure super-admin/import and student-submission branches still need individual runtime coverage. This audit does not certify cloud durability of local-first modules.

## How to read the cost model

- `C`: one awaited callable including server processing; `W`: an awaited Firestore write/transaction; `R`: a document/query read; `L`: Room work; `U`: image preparation/upload; `A`: awaited staff activity log (local insert plus cloud write).
- These are dependency models, **not stopwatch values**. A callable may contain many server reads/writes. Cache hits may avoid a network request. Retries add time.
- `N`: number of records. The strongest opportunities replace repeated network waits with validated batch operations, not merely faster animations.
- An audit log can leave the visible completion path only after a durable local outbox has recorded it. An untracked coroutine is not a reliable replacement.

## Most important findings

### 1. Bulk operations scale with sequential network acknowledgements

Attendance mark-all, ordinary exam result save/publish, final-exam fee generation and shift-all each contain awaited operations inside loops. For N items, cost includes approximately `sum(W_i)` or `sum(C_i)`, not one request. Fifty records can mean fifty waits. Batching does not eliminate the server's document writes, rule checks or transaction work.

Illustration only: **if** a measured write acknowledgement were 300ms, 50 sequential acknowledgements would contribute about 15 seconds. This is not BatchFee's measured time. A safe batch could remove 49 client round-trip boundaries for that group, but the result is not guaranteed to finish in 300ms. Batch size must respect payload, security-rule and atomicity requirements. Bulk financial operations need resumable progress and per-item outcomes, not arbitrary client parallelism.

### 2. Staff audit logging can delay a successful action

`StaffActivityLogger.kt:20` returns immediately for owners. For staff it inserts Room history and awaits `AuditLogSyncHelper.upsertAuditLog` before returning. Many UI methods call it before `onSuccess`. The possible saving is the measured cloud-log acknowledgement time `A_cloud`, not all of save time. Staff login has a similar separate log block.

Important: `login_total_ms` is logged **before** that staff-login log and before `onSuccess`. It undercounts staff-visible completion and does not measure the first usable dashboard frame. Owner login tracking is already nonblocking and should not be misidentified as the same issue.

### 3. Institute profile “background” sync is actually awaited

`withContext(Dispatchers.IO)` moves execution off the main thread; it does **not** stop the caller waiting. The text-profile branch waits before closing. Busy state is reset after the suspending snackbar. Logo retry inserts 600ms + 1200ms between failures. Neither search debounce (250ms in StaffViewModel) nor dashboard ticker delays explain general save latency.

### 4. Full refresh is an indirect cost, not every save's critical path

`InstituteCacheRefreshManager` already offers background refresh and scoped deduplication. Many screen loaders use the background method, so it is wrong to add all full-refresh time to every save. However `CoreDataSyncCoordinator.kt:31` performs many modules sequentially, while cache freshness can be marked despite swallowed errors. Background reads can compete with writes and UI data delivery. Measure overlap; use targeted canonical updates and truthful freshness. Do not remove bootstrap needed after reinstall.

### 5. Fast-looking local success can hide sync failure

Templates/works/local-only final-exam/routine methods are not equivalent to server-confirmed fee saves. Shared operational helpers suppress certain permission errors. Fix truthful completion/retry semantics before using local-first as a universal speed technique. No optimization should hide a failed fee, credential, enrollment or published-work operation.

## Measurement plan required to answer exact seconds saved

Use debug/staging accounts and synthetic data, never client production edits as a benchmark. Per action record monotonic timestamps for: tap, validation end, upload end, request start/end, Room commit, audit queued/sent, callback, first usable rendered result. Use anonymous operation IDs; do not log names, passwords, tokens or phone numbers. Existing auth debug logging should be reviewed for sensitive fields before collecting traces.

Run owner/staff/student roles; warm and cold app; existing install and populated upgrade/reinstall; Wi-Fi and constrained network; success, failure/retry and reconnect; dataset sizes 10/50/200/1000 with safe server limits. At least 30 repeated samples per representative condition for an initial p50/p95 estimate, with larger samples where tails are unstable. Report failure/duplicate/data-loss rate alongside latency. No improvement is accepted if correctness degrades.

For each row calculate `saving = baseline completion p50/p95 - candidate completion p50/p95` under identical conditions. Track server-confirmed completion separately from local pending feedback. Proposed UX target: immediate progress feedback within 100ms under normal load; this is an engineering target, not an observed result or a guarantee of cloud completion.

## Recommended order (not implemented by this audit)

1. Instrument representative paths and fix misleading success/timing boundaries.
2. Bulk attendance + ordinary exam result batching, with rule/error/duplicate tests.
3. Durable staff-audit outbox and institute-profile completion/busy cleanup.
4. Resumable final-exam fee generation and shift-all (financial safety first).
5. Profile/account provisioning and media phases; cold/warm backend profiling.
6. Cache contention/freshness and local calculation/Room render performance.

No source optimization, production deploy, or release-readiness claim was made in this audit.

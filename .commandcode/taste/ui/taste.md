# UI/UX
- Use a light (not dark) theme for the student app — the UI should feel lighter and brighter. Confidence: 0.75
- Use clean sans-serif typography (Inter/Plus Jakarta Sans/SF Pro style), bold large styling for important numbers, and clear color contrast between headings and secondary labels. Confidence: 0.75
- Use soft rounded rectangles for feature cards with 12dp–16dp border-radius and subtle ambient blur shadows (no heavy drop shadows). Confidence: 0.70
- Use minimalist thin line icons (Feather Icons / Lucide style), flat vector — no gradients or 3D shapes. Confidence: 0.70
- Use a cohesive corporate color system: deep indigo/navy primary, muted pastel card backgrounds with saturated matching text/icons for status cards. Confidence: 0.70
- For month/date selection on mobile, prefer compact dialog/bottom-sheet pickers with a grid layout (e.g., 3×4 month grid + year navigation) over tall scrolling dropdown lists that cover most of the screen. Confidence: 0.75
- Attendance displays should use a monthly calendar grid (7-column day layout with day-of-week headers) rather than a flat chronological list. Each day cell shows the date number plus a color-coded status indicator: green check mark for present, red cross for absent, orange badge for late. Today's cell should be highlighted with a distinct border. Include month-navigation arrows and a summary row (Present/Absent/Late counts). Past days with no record should show a subtle placeholder (e.g., gray dash) rather than being blank. Confidence: 0.85
- When one selection field constrains another's valid range (e.g., Start Month → End Month, admission date → Start Month), visually dim the invalid options rather than removing them, and auto-correct downstream selections when the upstream constraint changes so an invalid range cannot remain selected. Confidence: 0.70
- Avoid misleading or inflated UI labels — don't badge a simple arithmetic calculation (e.g., `activeCount × avgPlanPrice`) as "PREDICTION · AI" or similar; use honest, descriptive labels like "MONTHLY ESTIMATE" that accurately reflect what the number represents. Confidence: 0.70
- Generated identity documents (ID cards, certificates, etc.) should emulate real-world institutional designs — specifically university ID cards as the visual benchmark. Key expected structural elements: institute branding (logo + name) in a colored header band, a circular photo area overlapping the header, an authorised signatory/authority signature line, issue and validity dates, and a clean two-column info layout for student details. Beyond structure, decorative shapes and patterns are essential for a polished/professional look: geometric background shapes (triangles, ovals, circles), subtle pattern overlays (diagonal stripes, wave patterns, grid dots), neon/glow effects, sweep-gradient rings around the photo, barcode strips, and emblem/seal graphics. The explicit goal is "eye-catching" and "professional." Confidence: 0.88
- Does not want "Are you sure?" confirmation dialogs for logout actions — logout should happen immediately without requiring an extra confirmation step. Confidence: 0.75
- Admin panel dialogs and sheets (extend subscription, plan details, confirmations, etc.) should be polished and professional — not bare text fields with simple buttons. Use: a header with an icon + title + subtitle, a current-status card showing relevant context (plan name, expiry, days remaining with color-coded indicators), quick-preset chips for common values, a live preview card showing the computed result before confirming, and properly styled confirm/cancel buttons with meaningful labels and disabled states. Confidence: 0.85
- User-facing in-app messages, warnings, and notifications should be in Bengali (Bangla), not English — the user provides Bengali copy for UI text and expects it to appear verbatim in the app. Confidence: 0.70
- Warning/alert banners on the dashboard should be non-blocking and dismissible — they inform without interrupting workflow. Use color-coding by urgency (red for critical ≤3 days, amber/yellow for moderate 4–7 days), include a close/✕ dismiss button, and position them below the header but above the main content so they're always visible when relevant. Confidence: 0.70
- When context needed for authentication/routing can be derived server-side (e.g., which institute a student belongs to, which email to use), do not require the end user to manually provide it — remove unnecessary fields from login forms and resolve them via backend lookup. The fewer fields an end user has to fill in, the better. Confidence: 0.75
- When the dashboard/home screen already has placeholder tiles or buttons for a feature (even if they currently show "coming soon"), wire the actual feature implementation into those existing affordances rather than routing through secondary navigation like a "More" tab. The dashboard is the primary surface for admin features; existing UI affordances on it are intentional entry points, not decorative placeholders. Confidence: 0.75
- All admin-side screens (add forms, list screens, detail views) must use the same dark color palette as the established DashboardScreen — matching background (`#07111F`), card (`#0F172A`), border (`#1E293B`), and accent colors exactly. New screens that introduce divergent color schemes (different backgrounds, different card colors, different accent hues) are treated as broken and need polishing to match. Confidence: 0.80
- Admin screens that create or assign content to students (homework, assignments, notices, exams, etc.) should include a batch/class/group selection dropdown to target specific student cohorts — not broadcast to all students by default. Batch targeting is an expected control, not an optional enhancement. Confidence: 0.75
- Avoid duplicating feature entry points across navigation surfaces — when a feature already has a tile/button on the Home Dashboard, do not also list it in the "More" tab or any secondary navigation menu. Duplicate paths confuse users about where to find things. Remove from secondary surfaces, keep the primary one. Confidence: 0.90
- Bulk "send all" messaging actions (SMS All, WhatsApp All, etc.) must not blindly message the entire list — open a recipient selection step first with individual select/deselect, Select All / Clear controls, a live selected-count, and per-recipient detail (name, phone, and domain-relevant info such as due amount or attendance status). Include domain-relevant quick group presets (e.g., an "Absent Only" button for attendance) so common cohorts can be selected in one tap. Confidence: 0.85
- For bulk messaging, prefer a semi-auto queue: send one recipient at a time with a configurable inter-message delay and a live progress tracker (Sent/Failed/Duplicate), rather than firing every message simultaneously. The user explicitly asks for a "bulk semi-auto" system, not an instant mass-send. Confidence: 0.75
- Bulk/semi-auto messaging systems should be built out consistently across every module that has per-student contact actions (fees, attendance, exams, etc.) — the user expects feature parity ("make all the systems") rather than single-send only in some modules and bulk in others. Confidence: 0.70
- Bulk/broadcast messages (SMS All, WhatsApp All) must be personalized per recipient — each student receives their own due details (name, total due, fee periods, itemized breakdown), never an identical message to everyone. "Message All" (personalized per-student) and "Broadcast" (same common message to everyone) must be two SEPARATE menu options with distinct semantics — not a single composer with an optional common part. Confidence: 0.85
- Personalized due-fee reminder messages must include a proper greeting ("Dear Guardian"), the student's name, and an explicit request to clear the due fees — not just a bare due report. Confidence: 0.85
- Generated exam result cards (shareable images) should be visually polished and professional — strong typography hierarchy, generous spacing, a gradient header band, and decorative background accents — not flat or plain. A plain-looking generated card is considered "falto" (poor quality) and must be redesigned even if it already contains all the required data fields. Confidence: 0.75
- Generated single-student result cards should favor a clean white/minimal theme (white background, a thin accent strip, soft gray content cards) over dense boxy navy panels and decorative background circles — busy color combinations/backgrounds read as cluttered ("khit khit") and are treated as a design flaw requiring redesign, even when all data fields are present. Polish should come from typography hierarchy and spacing rather than decorative density. Confidence: 0.75
- When sharing exam results for ALL students at once (the "All Results" action), prefer a single consolidated result-sheet PDF — one table containing every student, roughly 20-25 rows per page, with the header (institute logo/name, exam name, batch/subject/date, marks info) repeated on each page — over separate per-student cards or one-page-per-student PDFs. The table columns should include serial, student name, student ID, marks, grade, GPA, position, and a status/comment column. Confidence: 0.85
- Bulk/send-all messaging actions should be explicitly labeled by channel with dedicated buttons (e.g., separate "WhatsApp All" and "SMS All") rather than a single generic "Msg All" button that defers the channel choice to a follow-up step — when only a generic label existed, the user reported the buttons as missing/nonexistent. Confidence: 0.75
- Action buttons must carry a visible text label alongside any icon — icon-only buttons with no adjacent text are treated as broken because users cannot tell what the action does. Confidence: 0.85
- For data-entry grids where each record has optional components (MCQ/CQ/Practical/Total), render columns dynamically based on the configured components — hide columns for components that aren't applicable and cap at a small max (4 columns). Never render empty/irrelevant columns for unused components. Confidence: 0.70
- When a form field offers a dropdown of standard/preset options (e.g., Bangladesh exam names), also provide an editable text field so the user can rename/customize the selection rather than being locked to the preset list only. Confidence: 0.65
- Selection fields in create forms (exam name, subject name) should offer a dropdown pre-populated with comprehensive Bangladesh-standard option lists (school/college exam names; board subjects across Science/Humanities/Business/Technical) so the user can pick from a curated list rather than type free-form — the user requested this same dropdown pattern for both exam names and subject names. Confidence: 0.75
- Parent list cards (e.g., final exam cards) should surface a count of their related child records (e.g., a "N subjects" badge) so users can see at a glance how many sub-items have been created — not just the parent record's own metadata. Confidence: 0.70
- Values simplicity ("sahoje") as an explicit UI goal alongside "professional" and "eye-catching" — when a form/screen accumulates many input fields (field overload/clutter), the user asks whether it can be simplified rather than accepting the dense layout as-is. Confidence: 0.60
- When multiple related "create" actions of the same entity type exist (e.g., Regular Exam vs Final Exam), consolidate them behind a single entry point (a FAB) that opens a choice dialog with a per-option icon and short description, rather than separate entry points/buttons scattered across the screen. Confidence: 0.70
- Numeric data-entry fields tied to a configurable limit (e.g., exam marks vs. a configured full-marks value) must enforce that limit — out-of-range input should be flagged with red error highlighting (field border + row) and blocked at save with a message listing the offending rows, rather than silently accepting any value. Confidence: 0.85
- Input fields with a fixed maximum (e.g., full marks) should surface that maximum as a placeholder hint inside the field so the limit is visible while typing. Confidence: 0.60
- For subject marks entry configured as "Total Only" (single aggregate mark instead of MCQ/CQ/Practical components), render a single total input field with total-limit validation rather than the per-component columns. Confidence: 0.65
- Irreversible lock/submit actions (e.g., "Submit Marks") should be gated by a confirmation dialog that clearly warns "once you submit, you will no longer be able to edit" — with a confirm button explicitly labeled as locking ("Submit & Lock") and a safe dismiss ("Keep Editing") — rather than submitting immediately on tap. Confidence: 0.75
- Exam result cards/marksheets must show a per-subject component breakdown (MCQ, CQ, and Practical marks) alongside each subject's total, not just a single aggregate total per subject — subjects without a given component should show a placeholder ("—") for that column. Confidence: 0.85
- In result cards/marksheets, display total marks as a bare number — do not append a denominator like "85 / 100"; the user explicitly wants only the total mark shown. Confidence: 0.85
- Subject-wise marks in a marksheet should be rendered as a proper table (header row + zebra-striped data rows) rather than loose "label: value" rows. Confidence: 0.80
- The marksheet/result card header should present the institute's full identity in a vertical stack — logo, institute name, then the address on its own line directly below the name, then contact info below that — with the exam name rendered large and prominent. Confidence: 0.80
- The student details section of a marksheet should include batch/class name, roll/ID, student name, guardian name, and contact number. Confidence: 0.80
- Marksheets/result cards should end with two signature blocks: one for the institute owner/authority and one for the guardian. Confidence: 0.85

- Marksheets should include a subject pass/fail summary box: if all subjects passed, show "All Subjects Passed" in green; if any failed, list the count and names of the failed subjects (e.g., "Failed Subjects (2): Physics, Chemistry") in a red-tinted box. Confidence: 0.80
- Marksheet tables need clearly visible cell borders/grid lines — a dark header bar plus vertical column separators and horizontal row lines — not just zebra striping; a border that can't be discerned is treated as needing polish. Confidence: 0.70
- Staff/teacher selection dropdowns should list only active staff (filter out inactive records) rather than showing the full staff roster — the user explicitly asks to show only active teachers/staff. Confidence: 0.70

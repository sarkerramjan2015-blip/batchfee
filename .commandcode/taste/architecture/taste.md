# Architecture

## Firestore Query Patterns
- When querying Firestore collections whose schema has evolved over time (new fields added after initial documents were created), avoid server-side filters or ordering on those newer fields — they silently exclude older documents that lack the field. Instead, fetch all documents without the filter/order and handle missing values client-side with safe defaults, then sort/filter in the client. For sorting specifically, use a fallback chain (e.g., `generatedAt` → `approvedAt` → `startDateMs`) where each subsequent field covers documents that lack the previous one. Confidence: 0.92
- When a `collectionGroup` query is used, anticipate that it may require a Firestore composite index that doesn't exist yet. Catch `FAILED_PRECONDITION` errors and surface the auto-generated index creation link to the user rather than crashing or silently failing — the link is included in the error details. Confidence: 0.75

## Firestore Security Rules
- When adding specific security rules for a subcollection path (e.g., `institutes/{id}/receipts/{doc}`), audit all broader wildcard rules in the same file that could overlap (e.g., `institutes/{id}/{collection}/{document=**}`). Since Firestore rules are OR-based, a permissive wildcard rule negates a restrictive specific rule — access that the wildcard grants cannot be taken away by a more specific rule. Confidence: 0.85
- When using `get()` to read a document in Firestore security rules, always guard with `exists()` first (e.g., `exists(/databases/.../docs/$(uid)) && get(...).data.field == ...`). Without the `exists()` check, `get()` on a missing document causes a runtime error in rule evaluation, which can silently deny access or produce unexpected results. Confidence: 0.85
- Before writing Firestore security rules that reference stored role/status values from a document (e.g., `get(...).data.role == 'SuperAdmin'`), verify the exact string value and casing from the actual codebase that writes those fields — don't assume the format. A casing mismatch makes the rule silently always-false. Confidence: 0.85

## Firestore Transactions
- Firestore transactions should include explicit precondition checks inside the transaction body (e.g., verify a request document's `status` is still `"pending"`) that cause the transaction to abort if conditions aren't met. Don't rely on atomicity alone to prevent invalid state transitions — the transaction must validate that the world is still in the expected state before proceeding. Confidence: 0.85

## Data Modeling
- When adding new fields to Firestore documents that the UI needs to display, create a proper Kotlin data class/DTO with typed fields and safe defaults rather than accessing raw `Map<String, Any>` entries inline in ViewModels or Composables. Display-relevant fields deserve typed models; Firestore-only ad-hoc maps are acceptable only for fields no UI consumes. Confidence: 0.80
- When backfilling a missing parent-entity identifier field (like `instituteId`) from a subcollection document, derive it from the document's Firestore path (`docRef.parent.parent?.id`) rather than from a separate query or from the document's own potentially-incorrect stored fields. The path is authoritative for parent identity. Confidence: 0.75

## Security Posture
- Financial records (receipts, billing history, transaction logs) should default to owner-only access. Staff, subordinate roles, or other institutes must not read them unless the user explicitly approves that access — never assume financial data should be visible to non-owners by default. Confidence: 0.80
- For operations that must never be duplicated (approvals, payments, extensions), use defense in depth: server-side idempotency (deterministic document IDs + transactions with precondition checks) AND client-side guards (disable the trigger button during processing with a boolean state flag). One layer alone is insufficient. Confidence: 0.80

## Backend Architecture
- Prefer Cloud Functions (Firebase backend / trusted environment) for sensitive write operations that regular client users shouldn't perform directly (e.g., generating official receipts, modifying subscription state). When no Cloud Function exists, use narrowly-scoped Firestore rules with field-level validation as a fallback — never grant broad client-side write access to compensate for the missing backend. Confidence: 0.80


- Prefer read-only computation over database row generation for derived/displayed values. When a number (like outstanding due) can be calculated dynamically from existing data (admission date + fee rate + payment records), compute it — don't auto-create rows just to display a total. Only persist rows that have independent existence (e.g., an actual payment made). Confidence: 0.80
- Place new business logic utilities in the `domain/` package as standalone Kotlin `object` singletons rather than embedding them in ViewModels or Repositories — follow the existing `SessionManager`/`MonthlyDueCalculator` pattern. Confidence: 0.70
- Centralize shared business logic (especially data-generation/backfill routines) at a single bootstrap or post-login entry point, and let all screens consume the resulting data as passive readers — do not scatter the same generation logic across multiple screens as independent triggers. Confidence: 0.80
- When a computed value (like outstanding due) must be consistent across multiple screens and changes dynamically with user edits, have every screen call the same domain function rather than each implementing its own filter or inline calculation — a single source of truth at the function level prevents screen-to-screen drift. Confidence: 0.85
- When data generation is required for correct first-paint state, run it synchronously inside the bootstrap/loading phase before flipping the "ready" flag — never show a stale/zero state that will silently update moments later. The loading screen must cover all preparatory work. Confidence: 0.85
- When inserting rows that concurrent callers could target for the same logical key, prefer genuinely atomic approaches — deterministic primary keys (so Room resolves duplicates at the DB constraint level via OnConflictStrategy.REPLACE) rather than count-then-insert patterns which have a TOCTOU race window. Confidence: 0.85
- For Firestore documents that must never be duplicated (e.g., one trial receipt per institute), use a deterministic document ID (e.g., `"${instituteId}_trial"`) rather than relying on timestamp/random IDs plus query-before-create guards. The Firestore document ID itself is the idempotency key — a second write to the same ID overwrites, preventing duplicates at the storage level. Confidence: 0.85
- Never invent or guess financial data (dates, amounts, liabilities) when a required relationship is missing — skip the affected entity and log a warning instead. Financial integrity demands that missing data produces no record rather than a guessed record. Confidence: 0.90
- When a derived display list (like due fees) requires items that have no corresponding database rows (e.g., an unpaid month with no FeeEntity yet), synthesize read-only computed data objects (via a domain `data class` like `ComputedMonthDue`) rather than generating missing database rows. The display layer treats real and computed items uniformly; computed items must never be persisted. Confidence: 0.85
- For PDF generation with multiple stacked sections, declare named height constants at the top, compute total page height as their sum plus gaps, and advance the y-position by `sectionHeight + gap` after each section — this eliminates overlap bugs caused by hardcoded or estimated y-offsets. Confidence: 0.80
- When passing data to a domain calculator that needs to detect completed/resolved states (e.g., MonthlyDueCalculator checking which months are already paid), feed it ALL records including zero-balance ones — not just active/outstanding records. Apply the `dueAmount > 0` filter only at the display layer, never at the computation input layer. Confidence: 0.85
- When a discount is applied to a fee, the discounted portion must never reappear as outstanding due — discounts are permanent reductions (persisted in the FeeEntity's `discountAmount`), not temporary deferrals. The due computation must treat the post-discount amount as the effective payable, not the original base amount. Any multi-month distribution of a discount must proportionally set `discountAmount` on each per-month fee record so the calculator can see the reduction. Confidence: 0.85
- Discount functionality must be uniformly available across all fee types (monthly, admission, advance, one-time) — no fee type should be hardcoded to `discountAmount = 0.0`. If a discount UI exists for one fee type, it should exist for all. Confidence: 0.80
- Security/authorization gates (subscription checks, access control, license validation) must fail closed (deny access) when the primary check fails, not open (allow). On network error, exhaust local fallback (Room DB) before making a decision; if all data sources are unavailable, deny access — never return `false`/allowed from a catch block. Confidence: 0.85
- Time-sensitive authorization state (subscription expiry, trial end, license validity) must be re-validated periodically during active sessions, not checked only at the initial entry gate (login/splash). Add re-check ticks to existing heartbeat/interval loops rather than introducing new timers. Confidence: 0.80
- When a remote data source (Firestore) is unreachable for an authorization decision, fall back through a local degradation chain: remote → Room/local-DB cache → safe default (deny). Each tier must be explicitly checked before falling through; skip tiers only when the data to answer the question doesn't exist at that tier. Confidence: 0.80
- For admin operations that require credential re-verification (remove/delete, sensitive config changes), use Firebase Auth `reauthenticate()` with `EmailAuthProvider.getCredential()` rather than comparing against locally-stored password hashes via `PasswordHasher.verify()`. Firebase Auth is the authoritative credential source; Room-stored hashes may be empty or stale, especially for users created via backfill/import — and a failed local check silently blocks the operation. Confidence: 0.75
- When admin approval actions produce receipts/documents intended for the target entity (institute, student, etc.), persist them server-side (Firestore subcollection) rather than keeping them only in ephemeral app state — documents must survive dialog dismissal and be retrievable from the entity's own dashboard, not vanish when the admin closes a popup. Confidence: 0.80
- When a Firestore document needs to support both global/cross-entity queries (e.g., superadmin listing all receipts across institutes) and scoped per-entity queries (e.g., a single institute's dashboard), use a dual-write pattern: persist the same document to both a top-level collection (`subscription_receipts`) and the entity's subcollection (`institutes/{id}/receipts/{num}`). Each collection serves its own query pattern without requiring collection-group indexes or client-side filtering. Confidence: 0.30
- Free trial/zero-amount signup events should generate a receipt record in the entity's `receipts/` subcollection — the user treats every subscription event (paid or trial) as a receipt-worthy financial record. No subscription transition should be receipt-less. Confidence: 0.85
- When adding a data view for entity-owned records (receipts, payment history, transaction logs, etc.), ensure it is accessible from both the admin panel (super admin) AND the entity owner's own app — do not restrict such views to admin-only access. The entity owner should see their own data in their own interface, not rely on the admin to view it for them. Confidence: 0.75
- Prefer a single source of truth for Firestore data (e.g., `institutes/{id}/receipts/{doc}`) over dual-write to multiple collections. Use `collectionGroup` queries for cross-entity/admin listings rather than maintaining a parallel top-level collection. Dual-write creates non-atomic writes and risks drift between copies. Confidence: 0.85
- When multiple Firestore documents must be written atomically (e.g., updating a subscription status AND creating a receipt), use `firestore.runBatch {}` or `runTransaction {}` so both writes succeed or fail together — never chain independent `set().await()` calls for logically-coupled operations. Confidence: 0.85

- Prefer nesting entity-specific records (receipts, payment history, transaction logs) inside each entity's detail view/dialog rather than presenting them as a standalone flat global list on the admin dashboard. Contextualized per-entity views are more useful and avoid cluttering the main admin interface with long serial lists. Confidence: 0.80
- Never assume `auth.uid` equals an entity ID (instituteId, etc.) for authorization rules — explicitly trace the real mapping from authentication to entity ownership (e.g., via `app_users/{uid}.data.role` or an explicit owner field) before writing security rules or queries that depend on that mapping. Confidence: 0.80

- For asset/file storage (logos, images, any binary user content), prefer cloud-hosted solutions (Firebase Storage, etc.) with download URLs persisted to both cloud (Firestore) and local (Room) databases — not local file-only approaches that break on reinstall, cross-device, or cache-clear scenarios. The professional cloud route is preferred even when it's explicitly acknowledged as more time-consuming than a local workaround. Confidence: 0.75

- When a Flow `collect` block performs heavy computation (iterating through many records, computing derived values, nested loops over students/batches), offload the work to `Dispatchers.Default` with `withContext()` — heavy main-thread work inside a collector causes frame drops that freeze animations (shimmer, infinite transitions, etc.). Confidence: 0.75

- When an admin mutation changes entity state (extend subscription, approve request, modify dates/fields), synchronize all three data tiers atomically in the same operation: (1) Firestore — the remote source of truth, (2) Room/DB — the local cache, and (3) the in-memory StateFlow list — the live UI state. Don't update only Firestore and wait for a snapshot listener to eventually propagate the change; the UI and local cache must reflect the mutation immediately. Confidence: 0.80

- When a non-critical sub-operation fails after the primary operation succeeded (e.g., Firestore write succeeds but the local Room cache update throws), surface a warning to the user by appending a parenthetical note to the success message (e.g., "(local cache update failed)") rather than silently swallowing the failure or aborting the whole operation. The primary success should still be communicated; the warning informs without blocking. Confidence: 0.70

- Never use a hardcoded magic-string fallback for user/session identity (e.g., `"sys_super_admin_1"`) when the real identifier is unavailable. Throw an explicit `IllegalStateException` with a clear message instead — a missing identity is a hard failure that must be visible, and a hardcoded fallback silently attributes actions to a wrong or fake user. Confidence: 0.75

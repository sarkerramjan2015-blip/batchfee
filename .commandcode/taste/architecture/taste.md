# Architecture

## Firestore Query Patterns
- When querying Firestore collections whose schema has evolved over time (new fields added after initial documents were created), avoid server-side filters or ordering on those newer fields — they silently exclude older documents that lack the field. Instead, fetch all documents without the filter/order and handle missing values client-side with safe defaults, then sort/filter in the client. For sorting specifically, use a fallback chain (e.g., `generatedAt` → `approvedAt` → `startDateMs`) where each subsequent field covers documents that lack the previous one. Confidence: 0.92
- When a `collectionGroup` query is used, anticipate that it may require a Firestore composite index that doesn't exist yet. Catch `FAILED_PRECONDITION` errors and surface the auto-generated index creation link to the user rather than crashing or silently failing — the link is included in the error details. Confidence: 0.75
- User-facing screens (student dashboard, fees, results, profile, etc.) should use Firestore `addSnapshotListener` for real-time data rather than one-shot `get().await()` fetches — the user expects data to update live without manual refresh. All related subcollections (fees, attendance, results, homework, assignments) should be wired with snapshot listeners in `DisposableEffect` blocks. Confidence: 0.85

## Pre-Auth Lookup Collections
- When implementing login flows where the end user hasn't authenticated yet and therefore cannot query protected subcollections directly, use a dedicated top-level Firestore collection (e.g., `student_login_mappings`) with public-read rules that maps a simple user-provided key to all needed context (institute ID, stored email, display name, etc.). This avoids requiring the user to provide additional identification fields (like an institute code) that can be resolved server-side via the mapping document. The collection acts as a lightweight reverse-index for pre-auth context resolution. Confidence: 0.75
- When introducing a pre-auth lookup/index collection whose documents are created lazily at entity save time, always include a fallback query path that searches the source-of-truth data directly — existing entities created before the lookup system existed won't have mapping documents. The fallback should auto-populate the lookup document on first successful resolution so subsequent lookups use the fast path. Do not ship the fast-path-only version and wait for users to hit "not found" errors. Confidence: 0.80
- When the source-of-truth data for the fallback path lives behind Firebase Auth (i.e., unauthenticated users cannot read it), the fallback must authenticate FIRST (via predictable email patterns, then Firebase Auth sign-in), and only then query the protected data — never attempt to query protected Firestore collections while still unauthenticated. On success, create the lookup mapping; on failure, explicitly sign out to clean up the authenticated session. Confidence: 0.85
- When disabling access for an entity whose login is gated by a pre-auth lookup document, soft-delete by setting an `isAppAccessEnabled` boolean to `false` rather than actually deleting the document — this preserves the document so the login flow can read it and produce a clear rejection message (e.g., "App access is not enabled"), and prevents re-creation races where the document might be accidentally recreated after deletion. Confidence: 0.80
- When a pre-auth lookup collection can be populated from admin-side data, proactively sync it during normal authenticated workflows (e.g., admin viewing the entity list) — not just lazily at save time or reactively at login fallback. Existing entities created before the lookup system existed will have no mapping documents, and waiting for each entity to attempt login before populating the lookup means every user hits the slow fallback path at least once. Fire-and-forget the sync from the data-observation point (e.g., inside a Room `collect` block) so the lookup stays populated without blocking the UI. Confidence: 0.75
- When a pre-auth lookup document stores a credential (e.g., `appAccessEmail`) that points to a Firebase Auth account that no longer exists (deleted during an edit cycle, never created, etc.), implement auto-recovery in the login flow: detect the account-missing error, recreate the Firebase Auth account with the user-provided password, generate a fresh unique email, and update both the lookup mapping and the source-of-truth document with the new email — all in the same login attempt. Do not fail with an opaque "invalid credential" error when the account simply needs to be regenerated. Confidence: 0.75

## Firebase Auth
- When using Firebase Auth REST API (`createUser`, etc.) to programmatically create an account, the REST API only creates the account — it does NOT establish an authenticated session. Always follow up with an SDK `signInWithEmailAndPassword()` call in the same code path if the created user needs to be authenticated for subsequent operations (Firestore writes, etc.). Skipping this step leaves the user unauthenticated and causes silent failures on protected resources. Confidence: 0.85
- When the Android client SDK lacks a secure API to perform an operation on another user's Firebase Auth account (e.g., setting an arbitrary password without the target user's `idToken`), do NOT implement a deceptive partial workaround that appears to work but fails silently. Instead, redesign the flow honestly — use the correct Firebase-provided mechanism (e.g., `sendPasswordResetEmail`) or a backend/Cloud Function, and make the UX transparent to the admin about what's happening. Never ship a UI that lets the admin believe they've set a password when the actual Firebase Auth credential hasn't changed. Confidence: 0.90

## Firestore Security Rules
- When adding specific security rules for a subcollection path (e.g., `institutes/{id}/receipts/{doc}`), audit all broader wildcard rules in the same file that could overlap (e.g., `institutes/{id}/{collection}/{document=**}`). Since Firestore rules are OR-based, a permissive wildcard rule negates a restrictive specific rule — access that the wildcard grants cannot be taken away by a more specific rule. Confidence: 0.85
- When using `get()` to read a document in Firestore security rules, always guard with `exists()` first (e.g., `exists(/databases/.../docs/$(uid)) && get(...).data.field == ...`). Without the `exists()` check, `get()` on a missing document causes a runtime error in rule evaluation, which can silently deny access or produce unexpected results. Confidence: 0.85
- When writing Firestore security rules for a collection that can be written from multiple code paths with different auth identities (e.g., owner creates the mapping, but student auto-recovery updates it), match rules to ALL plausible auth contexts — not just the primary owner. A rule like `resource.data.instituteId == request.auth.uid` works for the owner but fails for the authenticated student during self-healing flows. Either relax the condition to `request.auth != null` or add an explicit allow for the secondary identity. Confidence: 0.85

## Firestore Transactions
- When multiple code paths write to the same Firestore document (e.g., admin-side sync vs. auth self-healing recovery), use `SetOptions.merge()` rather than plain `.set()` to avoid one path silently overwriting fields written by the other path. Full-document `set()` is appropriate only when a single path owns the document exclusively. Confidence: 0.75

## Data Modeling
- When adding new fields to Firestore documents that the UI needs to display, create a proper Kotlin data class/DTO with typed fields and safe defaults rather than accessing raw `Map<String, Any>` entries inline in ViewModels or Composables. Display-relevant fields deserve typed models; Firestore-only ad-hoc maps are acceptable only for fields no UI consumes. Confidence: 0.80
- When backfilling a missing parent-entity identifier field (like `instituteId`) from a subcollection document, derive it from the document's Firestore path (`docRef.parent.parent?.id`) rather than from a separate query or from the document's own potentially-incorrect stored fields. The path is authoritative for parent identity. Confidence: 0.75

## Error Handling
- Never silently swallow exceptions with a bare `catch (_: Exception) { }` block — failures must be surfaced to the UI/ViewModel layer via proper error reporting (`onError`, sealed result types, Snackbar, etc.). Discarding an error without any user-visible signal is never acceptable, even for "non-critical" operations. Confidence: 0.90

## Security Posture
- Financial records (receipts, billing history, transaction logs) should default to owner-only access. Staff, subordinate roles, or other institutes must not read them unless the user explicitly approves that access — never assume financial data should be visible to non-owners by default. Confidence: 0.80
- For operations that must never be duplicated (approvals, payments, extensions), use defense in depth: server-side idempotency (deterministic document IDs + transactions with precondition checks) AND client-side guards (disable the trigger button during processing with a boolean state flag). One layer alone is insufficient. Confidence: 0.80

## Backend Architecture
- Prefer Cloud Functions (Firebase backend / trusted environment) for sensitive write operations that regular client users shouldn't perform directly (e.g., generating official receipts, modifying subscription state). When no Cloud Function exists, use narrowly-scoped Firestore rules with field-level validation as a fallback — never grant broad client-side write access to compensate for the missing backend. Confidence: 0.80


- Prefer read-only computation over database row generation for derived/displayed values. When a number (like outstanding due) can be calculated dynamically from existing data (admission date + fee rate + payment records), compute it — don't auto-create rows just to display a total. Only persist rows that have independent existence (e.g., an actual payment made). Confidence: 0.80
- Place new business logic utilities in the `domain/` package as standalone Kotlin `object` singletons rather than embedding them in ViewModels or Repositories — follow the existing `SessionManager`/`MonthlyDueCalculator` pattern. Confidence: 0.70
- Centralize shared business logic (especially data-generation/backfill routines) at a single bootstrap or post-login entry point, and let all screens consume the resulting data as passive readers — do not scatter the same generation logic across multiple screens as independent triggers. Confidence: 0.80
- When a computed value (like outstanding due) must be consistent across multiple screens and changes dynamically with user edits, have every screen call the same domain function rather than each implementing its own filter or inline calculation — a single source of truth at the function level prevents screen-to-screen drift. Confidence: 0.85

- When filtering records by whether they are "past due" for calendar-month-based accounting (fees, subscriptions, recurring charges), use calendar-month boundary comparison (extract YearMonth from the record's period/date and compare against `Calendar.getInstance()` current YearMonth) rather than raw `timestamp < System.currentTimeMillis()`. Raw timestamp comparison incorrectly marks current-month items as "past due" the moment their individual due date passes, even though the current calendar month as a whole should never be treated as due. Only months strictly before the current calendar month count as past. Confidence: 0.90

- When data rows exist for future periods that should not appear in current-period calculations, exclude them at the query/filter layer — never delete or mutate the underlying rows. Future data must be preserved intact; only the computation/display layer should narrow the window. Confidence: 0.80
- When data generation is required for correct first-paint state, run it synchronously inside the bootstrap/loading phase before flipping the "ready" flag — never show a stale/zero state that will silently update moments later. The loading screen must cover all preparatory work. Confidence: 0.85
- When inserting rows that concurrent callers could target for the same logical key, prefer genuinely atomic approaches — deterministic primary keys (so Room resolves duplicates at the DB constraint level via OnConflictStrategy.REPLACE) rather than count-then-insert patterns which have a TOCTOU race window. Confidence: 0.85
- For Firestore documents that must never be duplicated (e.g., one trial receipt per institute), use a deterministic document ID (e.g., `"${instituteId}_trial"`) rather than relying on timestamp/random IDs plus query-before-create guards. The Firestore document ID itself is the idempotency key — a second write to the same ID overwrites, preventing duplicates at the storage level. Confidence: 0.85
- Never invent or guess financial data (dates, amounts, liabilities) when a required relationship is missing — skip the affected entity and log a warning instead. Financial integrity demands that missing data produces no record rather than a guessed record. Confidence: 0.90
- When a derived display list (like due fees) requires items that have no corresponding database rows (e.g., an unpaid month with no FeeEntity yet), synthesize read-only computed data objects (via a domain `data class` like `ComputedMonthDue`) rather than generating missing database rows. The display layer treats real and computed items uniformly; computed items must never be persisted. Confidence: 0.85
- For PDF generation with multiple stacked sections, declare named height constants at the top, compute total page height as their sum plus gaps, and advance the y-position by `sectionHeight + gap` after each section — this eliminates overlap bugs caused by hardcoded or estimated y-offsets. Confidence: 0.80
- When passing data to a domain calculator that needs to detect completed/resolved states (e.g., MonthlyDueCalculator checking which months are already paid), feed it ALL records including zero-balance ones — not just active/outstanding records. Apply the `dueAmount > 0` filter only at the display layer, never at the computation input layer. Confidence: 0.85
- When a percentage or rate is used to compute a derived financial value at display time (e.g., converting a discount percentage back to an absolute BDT amount), apply it to the original source field (e.g., `baseAmount`) — never to an already-transformed intermediate (e.g., `totalAmount` which is already net of discount). Computing `discountRate × alreadyDiscountedNet` produces a double-reduced wrong value. Always trace the computation back to the original, untransformed field. Confidence: 0.85
- Discount functionality must be uniformly available across all fee types (monthly, admission, advance, one-time) — no fee type should be hardcoded to `discountAmount = 0.0`. If a discount UI exists for one fee type, it should exist for all. Confidence: 0.80
- Security/authorization gates (subscription checks, access control, license validation) must fail closed (deny access) when the primary check fails, not open (allow). On network error, exhaust local fallback (Room DB) before making a decision; if all data sources are unavailable, deny access — never return `false`/allowed from a catch block. Confidence: 0.85
- Time-sensitive authorization state (subscription expiry, trial end, license validity) must be re-validated periodically during active sessions, not checked only at the initial entry gate (login/splash). Add re-check ticks to existing heartbeat/interval loops rather than introducing new timers. Confidence: 0.80
- When a remote data source (Firestore) is unreachable for an authorization decision, fall back through a local degradation chain: remote → Room/local-DB cache → safe default (deny). Each tier must be explicitly checked before falling through; skip tiers only when the data to answer the question doesn't exist at that tier. Confidence: 0.80
- For admin operations that require credential re-verification (remove/delete, sensitive config changes), use Firebase Auth `reauthenticate()` with `EmailAuthProvider.getCredential()` rather than comparing against locally-stored password hashes via `PasswordHasher.verify()`. Firebase Auth is the authoritative credential source; Room-stored hashes may be empty or stale, especially for users created via backfill/import — and a failed local check silently blocks the operation. Confidence: 0.75
- When admin approval actions produce receipts/documents intended for the target entity (institute, student, etc.), persist them server-side (Firestore subcollection) rather than keeping them only in ephemeral app state — documents must survive dialog dismissal and be retrievable from the entity's own dashboard, not vanish when the admin closes a popup. Confidence: 0.80
- When a Firestore document needs to support both global/cross-entity queries (e.g., superadmin listing all receipts across institutes) and scoped per-entity queries (e.g., a single institute's dashboard), use a dual-write pattern: persist the same document to both a top-level collection (`subscription_receipts`) and the entity's subcollection (`institutes/{id}/receipts/{num}`). Each collection serves its own query pattern without requiring collection-group indexes or client-side filtering. Confidence: 0.30
- Free trial/zero-amount signup events should generate a receipt record in the entity's `receipts/` subcollection — the user treats every subscription event (paid or trial) as a receipt-worthy financial record. No subscription transition should be receipt-less. Confidence: 0.85
- When adding a data view for entity-owned records (receipts, payment history, transaction logs, etc.), ensure it is accessible from both the admin panel (super admin) AND the entity owner's own app — do not restrict such views to admin-only access. The entity owner should see their own data in their own interface, not rely on the admin to view it for them. Confidence: 0.75
- Prefer a single source of truth for Firestore data (e.g., `institutes/{id}/receipts/{doc}`) over dual-write to multiple collections. Use `collectionGroup` queries for cross-entity/admin listings rather than maintaining a parallel top-level collection. Dual-write creates non-atomic writes and risks drift between copies. Confidence: 0.85
- When multiple Firestore documents must be written atomically (e.g., updating a subscription status AND creating a receipt), use `firestore.runBatch {}` or `runTransaction {}` so both writes succeed or fail together — never chain independent `set().await()` calls for logically-coupled operations. Confidence: 0.85

- Prefer nesting entity-specific records (receipts, payment history, transaction logs) inside each entity's detail view/dialog rather than presenting them as a standalone flat global list on the admin dashboard. Contextualized per-entity views are more useful and avoid cluttering the main admin interface with long serial lists. Confidence: 0.80
- Never assume `auth.uid` equals an entity ID (instituteId, etc.) for authorization rules — explicitly trace the real mapping from authentication to entity ownership (e.g., via `app_users/{uid}.data.role` or an explicit owner field) before writing security rules or queries that depend on that mapping. Confidence: 0.80

- When implementing entity deletion (student, staff, institute, etc.), cascade to ALL related data types — not just the main record. Enumerate every related subcollection/table (fees, payments, receipts, attendance, exam results, batch enrollments, auth accounts, lookup/index mappings, etc.) and ensure none are left orphaned after deletion. Present a complete audit of what is and isn't covered before shipping deletion functionality. Confidence: 0.70
- When cleaning up secondary/index/lookup documents as part of a primary transaction (e.g., deleting `student_login_mappings` after student deletion), wrap the cleanup in try-catch and treat it as best-effort — the secondary cleanup must never fail or roll back the primary operation. Place it after the primary transaction completes, not inside it. Confidence: 0.75

- For asset/file storage (logos, images, any binary user content), prefer cloud-hosted solutions with download URLs persisted to both cloud (Firestore) and local (Room) databases — not local file-only approaches that break on reinstall, cross-device, or cache-clear scenarios. Confidence: 0.75
- For image hosting specifically on free-tier Firebase projects (where Firebase Storage requires a paid Blaze plan), prefer Cloudinary's free tier over Firebase Storage — the same durability/recovery guarantees (HTTPS URL → Firestore → Room → local cache) are achievable without the cost. Upload locally first, then to Cloudinary; the resulting URL flows through the standard save-then-sync pipeline. Confidence: 0.80

- When saving user-edited data that must survive across sessions (profile info, settings, uploaded asset URLs), persist to the local database (Room) FIRST as the primary durability mechanism, then attempt remote sync (Firestore) as a best-effort follow-up. Never gate the local save on remote success — a network failure should not prevent the user's changes from being persisted locally, and the remote sync can catch up on the next successful connection or refresh cycle. Confidence: 0.80
- Authentication credentials (passwords, tokens, auth state) are an exception to the "local first" rule: the remote auth provider (Firebase Auth) is the source of truth. Do NOT update local password hashes or credential stores before the remote auth operation succeeds — doing so creates a window where local and remote are inconsistent, and if the remote operation fails, the local store has a password that will never work. Confidence: 0.90

- Always set explicit timeouts on `OkHttpClient` instances — especially for upload operations that run on slow mobile networks. Use generous values (e.g., 30s connect, 60s read, 30s write) rather than relying on OkHttp's default 10-second timeouts, which are too aggressive for image uploads over 3G/4G connections. Confidence: 0.70

- When a Flow `collect` block performs heavy computation (iterating through many records, computing derived values, nested loops over students/batches), offload the work to `Dispatchers.Default` with `withContext()` — heavy main-thread work inside a collector causes frame drops that freeze animations (shimmer, infinite transitions, etc.). Confidence: 0.75

- When a ViewModel `combine`/`collect` block delegates to a data-processing function that could throw (e.g., `SimpleDateFormat` on invalid values, `Calendar` arithmetic on corrupt timestamps), wrap the COLLECT block in try-catch so an unhandled exception doesn't crash the app. However, a `try-catch` around the outer `viewModelScope.launch` does NOT catch exceptions thrown from inside the `combine` lambda — exceptions inside `combine` propagate through the Flow internally, bypassing the `launch`-level catch. The `try-catch` must be placed INSIDE the `combine` lambda itself: `combine(...) { a, b -> try { buildData(a, b) } catch (_: Exception) { } }.collect { ... }`. Confidence: 0.85
- When a ViewModel loads multiple database Flows (exam, subjects, marks, etc.) into separate state fields, do NOT `collect` them sequentially in the same coroutine body — the first `collect` suspends forever (it never completes), so every flow after it never runs and the screen renders empty/missing data. Launch each independent flow in its own child coroutine (`launch { db.dao().getX().collect { ... } }` inside the parent `viewModelScope.launch`) so they run concurrently and each state field gets populated. Confidence: 0.85

- When filtering data by date/timestamp fields for display (period filters, time-range queries), always guard against zero or null values (`dateMs > 0`) before passing values to date-formatting or calendar APIs — corrupt/invalid data should be silently excluded rather than allowed to crash downstream formatting code. Confidence: 0.75

- When a non-critical sub-operation fails after the primary operation succeeded (e.g., Firestore write succeeds but the local Room cache update throws), surface a warning to the user by appending a parenthetical note to the success message (e.g., "(local cache update failed)") rather than silently swallowing the failure or aborting the whole operation. The primary success should still be communicated; the warning informs without blocking. Confidence: 0.70

- Never use a hardcoded magic-string fallback for user/session identity (e.g., `"sys_super_admin_1"`) when the real identifier is unavailable. Throw an explicit `IllegalStateException` with a clear message instead — a missing identity is a hard failure that must be visible, and a hardcoded fallback silently attributes actions to a wrong or fake user. Confidence: 0.75

## Room Schema Evolution
- When adding a new field to a Room `@Entity` data class, update ALL tiers in the same pass: the entity class itself, a Room migration + database version bump, the Firestore sync helper (`toMap()` and `fromSnapshot()`), ViewModel/repository method signatures that construct or copy the entity, and all UI call sites that pass arguments to those methods. Partial updates that leave some tiers stale cause runtime crashes or silent data loss. Confidence: 0.70

## App Architecture
- All user types (admin, staff, student, etc.) must share a single Android app module with role-based navigation — different roles see different screens after login, but the APK is always one. Never create separate app modules or APKs for different user roles. The main AuthScreen acts as the universal entry point with role-specific login options (buttons/links). Use separate session managers (e.g., `SessionManager` for admin, `StudentSessionManager` for students) persisted in SharedPreferences to track which role is currently active. Confidence: 0.95

## Jetpack Compose State Management
- Use `mutableStateListOf()` (not `mutableStateOf(mutableListOf())`) for observable lists that will be mutated via `.add()`/`.removeAt()` in Jetpack Compose — mutating a plain `mutableListOf` held inside `mutableStateOf` does not trigger recomposition, so an "Add" button appears dead and the UI never updates. Confidence: 0.85
- For nested observable lists in Compose (e.g., a list-of-lists where each inner list is mutated independently via add/remove), each INNER list must also be an observable list (`SnapshotStateList` via `mutableStateListOf()`) — a plain `MutableList` nested inside an outer `mutableStateListOf` will not trigger recomposition when only the inner list mutates, so add/delete appears slow or stuck until an unrelated state change. Confidence: 0.80
- Hold mutable form/draft state as an immutable `data class` with `val` fields and update it via `copy()` assigned back to the list index, rather than a `class` with `var` fields mutated in place — immutable + `copy()` updates trigger recomposition reliably and prevent stale UI. Confidence: 0.75

## Feature Integration & Approval Workflows
- When extending an existing module with a new feature (e.g., adding a Final Exam module on top of the existing exam system), reuse the existing entities and data — students, subjects, teacher/staff, and institute-owner records — rather than creating a separate parallel system. The user explicitly forbids building a new standalone system when the feature can integrate with existing data. Confidence: 0.85
- Derived numeric fields that are sums or rankings of other inputs (subject totals, grand totals, percentage, GPA, grade, merit position) must be auto-calculated by the system and kept read-only — never allow manual entry of a value the system can compute. Total columns are always non-editable. Confidence: 0.85
- Exam subject marks should support per-component breakdown: when a subject uses MCQ/CQ/Practical components, each enabled component gets its own full-marks input field, and the subject total is auto-computed as the sum of enabled components (read-only). A distinct "total only" mode (single total-marks input) should cover subjects that don't use component breakdowns. The user treats MCQ/CQ/Practical as having potentially different marks rather than one shared total. Confidence: 0.80
- Exam subjects with MCQ/CQ/Practical components need per-component PASS marks as well — a separate "MCQ Pass", "CQ Pass", and "Practical Pass" field alongside each component's full-marks field, in addition to the overall pass mark. A single shared pass threshold for the whole subject is insufficient. Confidence: 0.80
- Multi-step approval workflows should distinguish a non-final Save (an editable draft the user can return to and revise freely) from an explicit Submit/Lock action that finalizes and blocks further edits — and show a confirmation dialog before that irreversible lock warning that editing will no longer be possible afterward. Once submitted, lock editing for the submitting role, keep an approval gate before the next stage (Draft → Submitted → Under Review → Approved → Published), and preserve the owner/privileged role's edit rights even after approval — with every privileged post-approval edit recorded in an audit log. Confidence: 0.85
- Aggregate/derived results (final results, reports, merit lists) must only be generated from approved data — gate result generation on all required records being approved, never compute from draft/submitted/pending data. Confidence: 0.75
- When a privileged/owner role edits records that are already submitted/under-review/approved, preserve the existing status and its timestamps (submittedAtMs, reviewedAtMs, approvedAtMs) rather than resetting the record back to a lower status (e.g., "draft") on save — never downgrade a submitted/approved record just because it was edited. Only brand-new or genuinely draft records should be written as "draft". Confidence: 0.80
- When adding a new feature that is a variant of an existing one, extend additively rather than replacing: add the new option inside the existing entry point and keep the existing workflow fully functional — the user explicitly requires the existing system to keep working exactly as before ("replacement নয়"). Confidence: 0.80
- For schedule/timetable features with multiple entries per time block, validate that time ranges within the same block do not overlap and reject end-time ≤ start-time; block save with a message naming the exact clashing entries rather than silently accepting conflicts. Confidence: 0.75
- Grouped child-record forms (e.g., classes per day) must support zero-to-many entries per group with no hardcoded maximum, and empty groups are valid — the user explicitly forbids fixed per-group caps. Confidence: 0.70
- Staff attendance should be segmented by how the staff member is paid: salaried/monthly staff (including monthly teachers) use simple daily presence marking (present/absent/leave/holiday), while per-class/per-hour teachers need per-class completion records (teacher, batch, subject, duration) with payment auto-calculated class-wise (per-class → rate × 1; per-hour → rate × minutes ÷ 60) from those records rather than entered manually. Confidence: 0.85

## Feature Flags & Institute Settings
- New optional features behind an ON/OFF toggle should default to OFF. Toggling the feature OFF must only hide its UI — it must not delete the underlying data — and toggling it back ON must reveal previously-entered data again. Never destroy data on toggle-off. Confidence: 0.85
- In this multi-institute app, feature toggles and settings should be institute-level (per-institute), and only the institute owner may change them — not app-global and not staff-editable. Confidence: 0.80

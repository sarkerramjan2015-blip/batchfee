# Architecture
- Prefer read-only computation over database row generation for derived/displayed values. When a number (like outstanding due) can be calculated dynamically from existing data (admission date + fee rate + payment records), compute it — don't auto-create rows just to display a total. Only persist rows that have independent existence (e.g., an actual payment made). Confidence: 0.80
- Place new business logic utilities in the `domain/` package as standalone Kotlin `object` singletons rather than embedding them in ViewModels or Repositories — follow the existing `SessionManager`/`MonthlyDueCalculator` pattern. Confidence: 0.70
- Centralize shared business logic (especially data-generation/backfill routines) at a single bootstrap or post-login entry point, and let all screens consume the resulting data as passive readers — do not scatter the same generation logic across multiple screens as independent triggers. Confidence: 0.80
- When a computed value (like outstanding due) must be consistent across multiple screens and changes dynamically with user edits, have every screen call the same domain function rather than each implementing its own filter or inline calculation — a single source of truth at the function level prevents screen-to-screen drift. Confidence: 0.85
- When data generation is required for correct first-paint state, run it synchronously inside the bootstrap/loading phase before flipping the "ready" flag — never show a stale/zero state that will silently update moments later. The loading screen must cover all preparatory work. Confidence: 0.85
- When inserting rows that concurrent callers could target for the same logical key, prefer genuinely atomic approaches — deterministic primary keys (so Room resolves duplicates at the DB constraint level via OnConflictStrategy.REPLACE) rather than count-then-insert patterns which have a TOCTOU race window. Confidence: 0.85
- Never invent or guess financial data (dates, amounts, liabilities) when a required relationship is missing — skip the affected entity and log a warning instead. Financial integrity demands that missing data produces no record rather than a guessed record. Confidence: 0.90
- When a derived display list (like due fees) requires items that have no corresponding database rows (e.g., an unpaid month with no FeeEntity yet), synthesize read-only computed data objects (via a domain `data class` like `ComputedMonthDue`) rather than generating missing database rows. The display layer treats real and computed items uniformly; computed items must never be persisted. Confidence: 0.85
- For PDF generation with multiple stacked sections, declare named height constants at the top, compute total page height as their sum plus gaps, and advance the y-position by `sectionHeight + gap` after each section — this eliminates overlap bugs caused by hardcoded or estimated y-offsets. Confidence: 0.80
- When passing data to a domain calculator that needs to detect completed/resolved states (e.g., MonthlyDueCalculator checking which months are already paid), feed it ALL records including zero-balance ones — not just active/outstanding records. Apply the `dueAmount > 0` filter only at the display layer, never at the computation input layer. Confidence: 0.85
- When a discount is applied to a fee, the discounted portion must never reappear as outstanding due — discounts are permanent reductions (persisted in the FeeEntity's `discountAmount`), not temporary deferrals. The due computation must treat the post-discount amount as the effective payable, not the original base amount. Any multi-month distribution of a discount must proportionally set `discountAmount` on each per-month fee record so the calculator can see the reduction. Confidence: 0.85
- Discount functionality must be uniformly available across all fee types (monthly, admission, advance, one-time) — no fee type should be hardcoded to `discountAmount = 0.0`. If a discount UI exists for one fee type, it should exist for all. Confidence: 0.80
- Security/authorization gates (subscription checks, access control, license validation) must fail closed (deny access) when the primary check fails, not open (allow). On network error, exhaust local fallback (Room DB) before making a decision; if all data sources are unavailable, deny access — never return `false`/allowed from a catch block. Confidence: 0.85
- Time-sensitive authorization state (subscription expiry, trial end, license validity) must be re-validated periodically during active sessions, not checked only at the initial entry gate (login/splash). Add re-check ticks to existing heartbeat/interval loops rather than introducing new timers. Confidence: 0.80
- When a remote data source (Firestore) is unreachable for an authorization decision, fall back through a local degradation chain: remote → Room/local-DB cache → safe default (deny). Each tier must be explicitly checked before falling through; skip tiers only when the data to answer the question doesn't exist at that tier. Confidence: 0.80
- For admin operations that require credential re-verification (remove/delete, sensitive config changes), use Firebase Auth `reauthenticate()` with `EmailAuthProvider.getCredential()` rather than comparing against locally-stored password hashes via `PasswordHasher.verify()`. Firebase Auth is the authoritative credential source; Room-stored hashes may be empty or stale, especially for users created via backfill/import — and a failed local check silently blocks the operation. Confidence: 0.75
